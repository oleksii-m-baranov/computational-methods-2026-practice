# 2. Класи аргументів інструментів (`arguments.py`)

У файлі `arguments.py` я створила окремі класи для перевірки аргументів кожного інструмента.

```python
"""Класи аргументів інструментів."""

from typing import Literal
from pydantic import BaseModel, ConfigDict, Field


class SearchBooksArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    query: str = Field(
        min_length=1,
        description="Жанр, тема або рівень складності книжки."
    )


class BookInfoArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    title: str = Field(
        min_length=1,
        description="Точна назва книжки з довідника."
    )


class CalculateArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    operation: Literal["mul", "add", "sub"] = Field(
        description="Операція: mul — множення, add — додавання, sub — віднімання."
    )

    a: float = Field(
        ge=0,
        description="Перше невід'ємне число."
    )

    b: float = Field(
        ge=0,
        description="Друге невід'ємне число."
    )


ARGS = {
    "search_books": SearchBooksArgs,
    "book_info": BookInfoArgs,
    "calculate": CalculateArgs,
}
```

У цих класах я вказала, які дані потрібно передавати кожному інструменту та які значення дозволені.

Для пошуку книжки потрібно передати текстовий запит `query`, а для отримання інформації про книжку — її назву `title`. Параметр `extra="forbid"` не дозволяє передавати зайві поля. Також я вказала, що текстові поля не можуть бути порожніми. Для інструмента `calculate` дозволила три операції: множення, додавання та віднімання. Числа `a` і `b` повинні бути не меншими за нуль.

# 8. Додаткове завдання: запобігання помилкам на сервері

Для перевірки я використала скрипт `structured_demo.py` та інструмент `calculate`. Схему передавала з класу `CalculateArgs` через `response_format`, а операція в ній обмежена переліком `Literal["mul", "add", "sub"]`.

Я запустила скрипт чотири рази з різними формулюваннями питання. Два питання стосуються операцій, які є в переліку, а два — ні.

| Питання | Відповідь моделі | Перевірка Pydantic | Чи правильна операція |
|---|---|---|---|
| Скільки буде 15 плюс 27? | `{"operation": "add", "a": 15, "b": 27}` | Пройшла | Так |
| Скільки буде 8 помножити на 6? | `{"operation": "mul", "a": 8, "b": 6}` | Пройшла | Так |
| Скільки буде 100 поділити на 4? | `{"operation": "mul", "a": 100, "b": 4}` | Пройшла | Ні: ділення немає в переліку, модель вибрала множення |
| Скільки буде 2 в десятому степені? | `{"operation": "sub", "a": 2, "b": 10}` | Пройшла | Ні: степеня немає в переліку, модель вибрала віднімання і взяла 10 замість степеня |

У всіх чотирьох випадках відповідь пройшла перевірку Pydantic. Але у двох із них операція неправильна. Перевірка не помітила цього, бо `mul` і `sub` дозволені схемою.

### Чи підтримує модель structured output?

Так. Модель повернула JSON, який відповідав схемі, і в усіх чотирьох відповідях операція належала до `mul`, `add`, `sub`. Це узгоджується з тим, що сервер обмежує вибір значень. Але чотирьох запусків недостатньо, щоб відрізнити обмеження на сервері від того, що модель просто так відповідала. 

### Чи можна прибрати перевірку в коді?

Ні. Structured output гарантує форму відповіді та дозволені значення, але не гарантує правильний вибір. У запиті про ділення модель не мала способу відповісти правильно, бо операції ділення в схемі немає. Вона вибрала найближчу дозволену операцію, і така відповідь проходить і сервер, і Pydantic. Так само сталося із степенем: модель вибрала `sub` і взяла 10 замість піднесення до степеня.

Тому перевірки змісту в коді потрібні. Вони мають перевіряти не лише формат, а й відповідність запиту. Наприклад, можна порівнювати результат інструмента з очікуваним значенням або перевіряти, що операція відповідає словам у запиті. Structured output зменшує кількість помилок форми, але помилок у змісті він не виявляє.
