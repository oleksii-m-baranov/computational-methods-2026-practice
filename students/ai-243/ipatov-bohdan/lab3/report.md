## 2. Класи аргументів трьох інструментів (`arguments.py`)

У попередній роботі схеми інструментів описувалися вручну і слугували лише підказкою для LLM, не гарантуючи дотримання типів. Для забезпечення суворої валідації в коді я реалізував опис аргументів через класи `Pydantic` у файлі `arguments.py`. Для кожного класу увімкнено `ConfigDict(extra="forbid")`, що додає у згенеровану JSON-схему директиву `"additionalProperties": false` і суворо забороняє моделі передавати непередбачені або вигадані поля.

```python
"""Pydantic argument schemas for library tools. Variant 11 (Library)."""
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field


class SearchBooksArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    query: str = Field(
        min_length=2,
        max_length=50,
        description=(
            "Одне ключове слово українською: жанр або тема "
            "(наприклад 'фантастика', 'алгоритми', 'сортування'). "
            "Не передавай цілі фрази, зайві слова чи все питання користувача."
        ),
    )


class BookInfoArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    title: str = Field(
        min_length=2,
        max_length=100,
        description=(
            "Точна офіційна назва книжки з результату пошуку search_books "
            "(наприклад 'Основи алгоритмів', 'Зоряний експрес')."
        ),
    )


class CalculateArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    operation: Literal["mul", "add", "sub"] = Field(
        description="Арифметична дія: mul (множення), add (додавання), sub (віднімання)",
    )
    a: float = Field(
        ge=0,
        le=100000,
        description="Перше число (наприклад, кількість днів)",
    )
    b: float = Field(
        ge=0,
        le=100000,
        description="Друге число (наприклад, ставка штрафу за день)",
    )


class IssueBookArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    title: str = Field(
        min_length=2,
        max_length=100,
        description="Назва книжки для видачі читачеві",
    )


ARGS = {
    "search_books": SearchBooksArgs,
    "book_info": BookInfoArgs,
    "calculate": CalculateArgs,
    "issue_book": IssueBookArgs,
}
```

## 3. Таблиця правил змісту

Для захисту даних і забезпечення логічної узгодженості дій агента я визначив сукупність правил, розділивши їх між структурною схемою Pydantic та семантичною перевіркою `check_meaning` у файлі `checks.py`:

### 6.3. Розбір двох трас

#### Траса 1: Модель помилилася, отримала повідомлення диспетчера і виправилася (`provoke-X1`)
Оскільки на 5 базових задачах модель не припустилася помилок у синтаксисі чи межах, згідно з інструкцією я сформулював провокаційний запит у файлі `recovery_demo.py` (траса `3a96692753770f165c999166b29507ec`):
> **Запит `provoke-X1`:** *«Порахуй штраф через calculate з operation='mul', a=-5, b=10.»*

![Траса provoke-X1 у Langfuse: помилка на рівні schema та самовиправлення моделі](screenshots/fixed_error_meaning.png)

- **Яка була помилка:** На кроці 1 модель викликала `calculate({"a": -5, "b": 10, "operation": "mul"})`. JSON синтаксично коректний, але значення `a = -5` порушує обмеження `ge=0` у Pydantic-класі `CalculateArgs`.
- **На якому рівні її зловлено:** Рівень **`schema`** (валідація меж поля `CalculateArgs.a` у `dispatcher.py`).
- **Яке повідомлення отримала модель:**
  ```text
  Помилка: аргументи не пройшли перевірку.
  Поле a: Input should be greater than or equal to 0
  Виправ аргументи і виклич інструмент ще раз.
  ```
- **Що змінила модель:** Отримавши зрозуміле 3-частинне повідомлення від диспетчера та збільшення лічильника `помилок поспіль = 1`, на кроці 2 модель виправила аргумент з `a = -5` на `a = 5` і повторно викликала `calculate({"a": 5, "b": 10, "operation": "mul"})` (`рівень = ok`, результат `50.0`). Лічильник `помилок поспіль` обнулився до `0`, а на кроці 3 модель сформувала правильну фінальну відповідь користувачеві (`50.0 гривень`).

## 7. Відповіді на контрольні питання

1. **Які поламки зникли або зменшилися після впровадження перевірок? Які лишилися?**  
   Кількість поламок зменшилася з 5 до 4, а успішність зросла з 40% до 60%: у задачі Z2 зникла поламка «Не викликав інструмент» — агент виконав обидва кроки (`search_books` та `book_info`) і дав правильну відповідь. У провокаційному тесті `provoke-X1` помилку `schema` (`a = -5`) було перехоплено та виправлено на `a = 5`. Лишилися пропуск `search_books`/`calculate` у Z3 та неправдива обіцянка у пастці P2.

2. **На якому рівні модель помилялася найчастіше? Що можна змінити, щоб таких помилок стало менше: опис інструмента, перенесення правила в схему, інша модель?**  
   На стандартних 5 задачах перевірки диспетчера не фіксували порушень формату чи назв (`0` помилок), а при штучному порушенні в `provoke-X1` спрацював рівень `schema` (`a = -5 < 0`). Критичною точкою для предметної області також є рівень `meaning` для `book_info`, якщо модель намагатиметься вгадати точну назву книги без `search_books`; для зменшення таких помилок важливі чіткі описи в `schemas.py` та підказки схожих назв через `difflib` у `check_meaning`.

3. **Чи траплялися відмови після ліміту помилок? Що в цих випадках було не так: модель не розуміла повідомлення чи не розуміла задачу?**  
   У прогоні на 5 задачах та в `provoke-X1` відмов через перевищення `MAX_RETRIES = 2` не було (Таблиця 4). У тесті `provoke-X1` модель уже на наступному кроці зрозуміла повідомлення про порушення межі `ge=0` та змінила `a = -5` на `a = 5`, скинувши лічильник помилок. Відмова за лімітом настає тоді, коли користувач наполягає на забороненій операції (наприклад, `issue_book`), а модель ігнорує заборону.

4. **Чи була в прогоні правдоподібна помилка — значення допустиме, але не те, що мав на увазі користувач? Чому жодна перевірка її не зловила?**  
   Так, у задачі P2 модель передала коректний запит `search_books({"query": "алгоритми"})` (`ok`), отримала реальну назву «Основи алгоритмів» і відповіла, що книжку нібито «збережено в бібліотеці», хоча бронювання немає взагалі. Також у Z1 модель передала двослівний рядок `"легке фантастика"`, що допустимо за типом `str` та довжиною, але дало порожній результат пошуку. Обидва значення формально валідні, тому перевірки схеми їх не блокують.

5. **Які поламки перевірки не лікують у принципі та чому?**  
   Перевірки в коді диспетчера в принципі не можуть вилікувати: 1) випадок, коли модель взагалі не викликала інструмент і перейшла в текст (у цьому разі управління не потрапляє в `call_tool`), 2) галюцинації у фінальному тексті (модель отримала дані, але вигадала факт у тексті), 3) хибний план міркувань за технічно валідних викликів (як `P2`). Диспетчер є фільтром на вході інструмента, а не валідатором сенсу текстової відповіді.

6. **Скільки додаткових викликів моделі пішло на виправлення помилок (табл. 6)? Чи виправдана така ціна надійності?**

## 8. Додаткове завдання: запобігання помилкам на сервері (`structured_demo.py`)

Я реалізував і запустив окремий скрипт `structured_demo.py`, який передає згенеровану JSON-схему `CalculateArgs` безпосередньо в параметр `response_format={"type": "json_schema", ...}` сервера Ollama:

### Результати експериментів у `structured_demo.py`:
1. **Стандартний запит:** *«Я затримав книжку на 5 днів, штраф становить 10 грн за день. Сформуй аргументи для розрахунку штрафу.»*  
   - Сира відповідь: `{ "operation": "sub", "a": 10, "b": 5 }`.  
   - Pydantic: `УСПІШНО -> operation='sub' a=10.0 b=5.0`.
2. **Числа словами:** *«Затримка сім днів, ставка штрафу п'ятнадцять гривень на добу. Сформуй аргументи для калькулятора.»*  
   - Сира відповідь: `{ "operation": "mul", "a": 15, "b": 5 }`.  
   - Pydantic: `УСПІШНО -> operation='mul' a=15.0 b=5.0`.
3. **Заборонена дія (ділення `div`):** *«Поділи сто на п'ять. Сформуй аргументи для калькулятора.»*  
   - Сира відповідь: `{ "operation": "sub", "a": 100, "b": 5 }`.  
   - Результат: серверний граматичний парсер Ollama заблокував `"div"` (відсутній у `Literal["mul", "add", "sub"]`) і змусив модель обрати допустиму операцію (`sub`).

**Висновки щодо structured output:**
Модель `qwen2.5:3b` в Ollama підтримує structured output на рівні граматики токенів, але сама по собі не гарантує семантичної правильності: наприклад, у першому запиті модель вибрала `"sub"` замість `"mul"`, а у другому сплутала число днів (`7` → `5`). Тому навіть за наявності серверного `json_schema` **прибирати перевірки в коді (`checks.py`, `dispatcher.py`) не можна** — сервер не знає бізнес-логіки й довідника `books.csv`.
