# 4. Підключення Langfuse

Для спостереження за роботою агента використано Langfuse.

У файлі `agent.py` підключено необхідні бібліотеки:

```python
from langfuse import observe, get_client
from openai import OpenAI
```

Основну функцію агента позначено декоратором:

```python
@observe()
def run_agent(task):
    ...
```

У файлі `agent_runner.py` використано контекст трасування:

```python
with propagate_attributes(
    trace_name=f"{config.RUN_TAG}-{task['id']}",
    tags=[config.RUN_TAG]
):
    result = run_agent(task["question"])
```

Після виконання тестових задач використовується:

```python
get_client().flush()
```

Це забезпечує передавання накопичених даних трасування до Langfuse.

# 5. Класи аргументів трьох інструментів

Для перевірки аргументів створено файл `arguments.py`.

Використано бібліотеку Pydantic, яка дозволяє задавати типи, обов'язкові поля та допустимі межі значень.

При цьому початкові описи інструментів із `schemas.py` залишено без змін.

## 5.1. Код файлу `arguments.py`

```python
from pydantic import BaseModel, Field, ConfigDict


class SearchLaptopsArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    query: str = Field(
        min_length=1,
        description="Текстовий запит для пошуку ноутбуків"
    )


class LaptopInfoArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    model: str = Field(
        min_length=1,
        description="Точна назва моделі ноутбука"
    )


class CalcInstallmentArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    price: float = Field(
        gt=0,
        description="Вартість ноутбука у гривнях"
    )

    months: int = Field(
        ge=1,
        le=60,
        description="Кількість місяців розстрочки"
    )

    overpay_percent: float = Field(
        ge=0,
        le=100,
        description="Відсоток переплати"
    )


ARGUMENT_MODELS = {
    "search_laptops": SearchLaptopsArgs,
    "laptop_info": LaptopInfoArgs,
    "calc_installment": CalcInstallmentArgs
}
```

## 5.2. Пояснення роботи класів

Клас `SearchLaptopsArgs` перевіряє, щоб аргумент `query` був непорожнім текстовим рядком.

Клас `LaptopInfoArgs` перевіряє наявність назви моделі ноутбука.

Клас `CalcInstallmentArgs` перевіряє числові параметри:

- `price` — ціна повинна бути більшою за нуль;
- `months` — кількість місяців від 1 до 60;
- `overpay_percent` — відсоток переплати від 0 до 100.

Параметр:

```python
model_config = ConfigDict(extra="forbid")
```

забороняє передавати невідомі поля.

Це дозволяє виявляти неправильні аргументи ще до виконання інструмента.

## 6.1. Перевірка змісту

Перевірка схеми не завжди гарантує правильність аргументів.

Наприклад:

```python
laptop_info({"model": "UnknownLaptop999"})
```

Цей виклик має правильний формат, але моделі `UnknownLaptop999` немає в довіднику.

Тому диспетчер повертає помилку рівня `meaning`.

Додатково реалізовано перевірку ціни під час розрахунку розстрочки.

У базовому прогоні модель отримала правильну ціну ноутбука `StudyNova 14` — 22000 грн, але передала до `calc_installment` значення 8000 грн.

Формально це додатне число, яке відповідає Pydantic-схемі, однак воно не відповідає фактичній ціні ноутбука.

Для усунення цієї проблеми реалізовано перевірку підтвердженої ціни через контекст агента.

Фрагмент коду `checks.py`:

```python
verified_price = context.get("verified_price")

if verified_price is None:
    return False, (
        "Перед розрахунком розстрочки необхідно "
        "отримати ціну через laptop_info. "
        "Виклич laptop_info, а потім calc_installment."
    )

if abs(float(price) - float(verified_price)) > 0.01:
    return False, (
        f"Невідповідність ціни: передано {price} грн, "
        f"але laptop_info підтвердив {verified_price} грн. "
        "Повтори розрахунок із підтвердженою ціною."
    )
```

Таким чином, система перевіряє не лише формат числового значення, а й відповідність ціни фактичним даним довідника.

# 7. Реалізація ланцюжка перевірок

У файлі `dispatcher.py` реалізовано послідовну перевірку викликів інструментів.

Основні рівні:

1. `name` — перевірка існування інструмента.
2. `permission` — перевірка дозволу.
3. `syntax` — перевірка синтаксису JSON.
4. `schema` — перевірка аргументів через Pydantic.
5. `meaning` — перевірка змісту.
6. `tool` — помилка виконання інструмента.
7. `ok` — успішне виконання.

## Таблиця 2 — Перевірка ланцюжка перевірок

| Що перевіряємо | Виклик | Рівень | Повідомлення для моделі |
|---|---|---|---|
| Зламаний JSON | `search_laptops({"query":` | `syntax` | Некоректний JSON. Виправити синтаксис |
| Неправильний тип | `search_laptops({"query":123})` | `schema` | Поле `query` повинно бути текстовим рядком |
| Відсутнє обов'язкове поле | `search_laptops({})` | `schema` | Необхідно додати поле `query` |
| Зайве поле | `search_laptops({"query":"навчання","extra":1})` | `schema` | Поле `extra` не дозволене |
| Неіснуючий інструмент | `unknown_tool({})` | `name` | Інструмент не знайдено |
| Заборонений інструмент | `place_order({"model":"StudyNova 14"})` | `permission` | Оформлення замовлення заборонено |
| Неіснуюча модель | `laptop_info({"model":"UnknownLaptop999"})` | `meaning` | Модель відсутня в довіднику |
| Значення поза межами | `calc_installment({"price":22000,"months":100,"overpay_percent":10})` | `schema` | Кількість місяців повинна бути від 1 до 60 |
| Непідтверджена ціна | `calc_installment({"price":22000,"months":6,"overpay_percent":10})` | `meaning` | Перед розрахунком необхідно отримати ціну через `laptop_info` |
| Невідповідність ціни | `calc_installment({"price":8000,"months":6,"overpay_percent":10})` | `meaning` | Передана ціна не відповідає підтвердженій |
| Правильна підтверджена ціна | `calc_installment({"price":22000,"months":6,"overpay_percent":10})` | `ok` | Розрахунок успішно виконано |

*Примітка: повідомлення наведені у скороченому вигляді зі збереженням їхнього змісту. Для останніх трьох тестів використовувався відповідний контекст ціни.*

# 8. Реалізація повторних спроб

Для запобігання нескінченному повторенню неправильних викликів реалізовано ліміт помилок.

У файлі конфігурації встановлено:

```python
MAX_RETRIES = 3
```

Якщо модель отримує помилку, її лічильник збільшується.

Якщо наступний виклик успішний, лічильник обнуляється.

Приклад логіки:

```python
if model_failed:
    retries += 1

    if retries > config.MAX_RETRIES:
        return None

elif tool_succeeded:
    retries = 0
```

Повідомлення про помилку передається моделі, щоб вона могла сформувати виправлений виклик.

Таким чином, повторна спроба виконується в основному циклі агента.

## 8.1. Виявлення помилки в задачі Z3

Під час виконання задачі Z3 модель отримала ціну ноутбука:


Помилка виникла через те, що `laptop_info` та `calc_installment` були викликані в одному кроці, а підтверджена ціна стає доступною для перевірки лише на наступному кроці.

# 10. Аналіз трасування Langfuse

Langfuse дозволяє досліджувати послідовність дій агента.

Для кожного кроку можна визначити:

- вхід;
- рішення;
- дію;
- результат;
- кількість токенів;
- час виконання.

## 10.1. Структура події

```text
Крок агента
    |
    v
Вхідні повідомлення
    |
    v
Рішення мовної моделі
    |
    v
Виклик інструмента
    |
    v
Результат виконання
```

**Крок** — одна ітерація роботи агента.

**Вхід** — завдання користувача та історія повідомлень.

**Рішення** — вибір інструмента та формування аргументів.

**Дія** — виконання `call_tool`.

**Результат** — відповідь інструмента або повідомлення про помилку.

## Таблиця 6 — Порівняння метрик Langfuse

| Задача | Викликів моделі: до | Викликів моделі: після | Токенів: до | Токенів: після | Час, с: до | Час, с: після |
|---|---|---|---|---|---|---|
| Z1 | 2 | 2 | н/д | н/д | н/д | н/д |
| Z2 | 3 | 3 | н/д | н/д | н/д | н/д |
| Z3 | 3 | 4 | н/д | н/д | н/д | н/д |
| P1 | 2 | 2 | н/д | н/д | н/д | н/д |
| P2 | 1 | 1 | н/д | н/д | н/д | н/д |
| **Разом** | **11** | **12** | **н/д** | **н/д** | **н/д** | **н/д** |

*Примітка: н/д — немає підтверджених даних останнього експерименту. Кількість викликів визначено за логами, а значення загальної кількості токенів і тривалості потрібно отримати з відповідних трас Langfuse. Старі метрики не перенесено, оскільки вони належали іншому прогону.*

# 12. Відповіді на питання

## 1. Які поламки зникли або зменшилися після впровадження перевірок? Які лишилися?

Після впровадження перевірок вдалося запобігти виконанню розрахунку з неправильною ціною ноутбука. У базовому прогоні модель використала ціну 8000 грн замість 22000 грн, а в режимі Checks диспетчер відхилив такий виклик і дозволив виконати правильний розрахунок. Водночас залишилася проблема P2: агент не повідомив прямо про недоступність резервування. Також у Z3 фінальна відповідь не повторила назву моделі ноутбука.

## 2. На якому рівні модель помилялася найчастіше? Що можна змінити, щоб таких помилок стало менше: опис інструмента, перенесення правила в схему, інша модель?

У повторному прогоні зафіксовано одну помилку рівня `meaning`. Інших помилок рівнів перевірки не було, тому саме цей рівень став єдиним зафіксованим. Для зменшення таких помилок можна уточнити опис інструмента, додати правило використання підтвердженої ціни та протестувати іншу мовну модель. У цій роботі реалізовано семантичну перевірку через контекст агента.

## 3. Чи траплялися відмови після ліміту помилок? Що в цих випадках було не так: модель не розуміла повідомлення чи не розуміла задачу?

У повторному прогоні відмов після перевищення ліміту помилок не зафіксовано. У задачі Z3 модель отримала повідомлення про помилку та виправила аргументи на наступному кроці. Тому в цьому експерименті немає підстав стверджувати, що модель не розуміла повідомлення або саму задачу.

## 4. Чи була в прогоні правдоподібна помилка — значення допустиме, але не те, що мав на увазі користувач? Чому жодна перевірка її не зловила?

Так. У базовому прогоні модель передала до `calc_installment` ціну 8000 грн замість 22000 грн. Значення 8000 є додатним і відповідає числовій схемі, тому звичайна перевірка типу та меж не виявила помилку. Після додавання семантичної перевірки система почала звіряти передану ціну з підтвердженою ціною ноутбука.

## 5. Які поламки перевірки не лікують у принципі та чому?

Перевірки не гарантують правильного вибору інструмента, повноти відповіді, правильного розуміння наміру користувача та достовірності кожного твердження у фінальному тексті. Вони контролюють формат, дозволи й допустимість аргументів, але не замінюють перевірку логіки розв'язання задачі.

## 6. Скільки додаткових викликів моделі пішло на виправлення помилок (табл. 6)? Чи виправдана така ціна надійності?

За таблицею 6 кількість викликів мовної моделі збільшилася з 11 до 12. Один додатковий виклик знадобився для виправлення помилки в задачі Z3. Така ціна надійності є виправданою, оскільки в результаті агент отримав правильний розрахунок розстрочки замість неправильного.

## 7. Візьміть найдовшу задачу. Що в ній легше побачити в трасі Langfuse, а що — у текстовому лозі? Чому на довгих задачах текстовий лог стає важко читати?

У режимі Checks найдовшою була задача Z3, яка складалася з чотирьох кроків. У Langfuse легше побачити структуру викликів, тривалість і взаємозв'язки подій, а в текстовому лозі — точні аргументи, рівні помилок і повідомлення диспетчера. На довгих задачах текстовий лог стає важко читати через велику кількість послідовних записів.

# 15. Питання для захисту

## 1. На які три рівні поділяють помилки у виклику інструмента? Наведіть приклад кожної зі свого прогону або з табл. 2.

Помилки можна поділити на помилки вибору інструмента, помилки аргументів і помилки виконання. Наприклад, `unknown_tool` — помилка назви інструмента, `{"query":123}` — помилка схеми, а збій під час виконання функції — помилка рівня `tool`.

## 2. Чому `call_tool` перевіряє існування і дозвіл інструмента раніше за аргументи?

Спочатку потрібно переконатися, що інструмент існує та його дозволено викликати. Немає сенсу перевіряти аргументи інструмента, який не існує або заборонений політикою доступу.

## 3. Що станеться, якщо в класі Pydantic не вказати `extra="forbid"`?

За типової конфігурації Pydantic зайві поля можуть ігноруватися. Це означає, що модель зможе передати невідомий аргумент, а перевірка схеми не повідомить про нього як про помилку.

## 4. Навіщо генерувати описи інструментів з класів Pydantic, а не писати їх вручну, як у лабораторній роботі № 2?

Генерування схем із Pydantic дозволяє уникнути розбіжностей між описом інструмента та правилами перевірки в коді. Якщо змінити клас аргументів, відповідна JSON-схема може бути оновлена автоматично. У повторному експерименті початкові описи `schemas.py` залишено без змін для забезпечення коректного порівняння з ЛР2.

## 5. Чому недостатньо просто не передавати моделі заборонений інструмент у `SCHEMAS`?

Модель може сформувати неправильну назву інструмента або спробувати викликати заборонену дію. Тому перевірка дозволів повинна виконуватися безпосередньо в диспетчері, незалежно від того, які інструменти були показані моделі.

## 6. Які правила змісту ви перенесли в класи, а які лишили в `check_meaning`? Чому?

У Pydantic-класи перенесено перевірки типів, обов'язкових полів і числових меж. У `check_meaning` залишено перевірку існування моделі в довіднику та відповідності ціни підтвердженим даним, оскільки ці правила залежать від фактичної інформації CSV-файлу й контексту виконання агента.

## 7. Чим помилка моделі відрізняється від помилки інструмента та чому повідомлення для них різні?

Помилка моделі виникає, коли вона неправильно вибирає інструмент або формує його аргументи. Помилка інструмента виникає під час виконання функції, тому моделі потрібно повідомити не про неправильний формат аргументів, а про проблему виконання.

## 8. Що ловить `check_response` і чому без цієї перевірки такий випадок виглядав як «не викликав інструмент»?

`check_response` перевіряє, чи відповідь моделі має очікувану структуру та чи не містить помилок формату або обмежень довжини. Без цієї перевірки некоректна відповідь могла б сприйматися як звичайна відсутність виклику інструмента.

## 9. Покажіть у коді, де відбувається повторна спроба. Чому для неї не потрібен окремий механізм і чому повторна спроба без пояснення помилки найчастіше не допомагає?

Повторна спроба відбувається в основному циклі `run_agent`, коли після помилки модель отримує нове повідомлення й виконується наступна ітерація. Окремий механізм не потрібен, оскільки цикл уже підтримує повторні звернення. Без пояснення помилки модель може знову сформувати той самий неправильний виклик.

## 10. Чим запобігання помилкам на сервері відрізняється від виявлення в коді? Чому навіть зі structured output перевірку в коді не прибирають?

Structured output обмежує формат відповіді ще під час генерації, а перевірки в коді аналізують уже отримані дані. Навіть зі structured output потрібно перевіряти дозволи, існування значень у довіднику та інші правила, які неможливо гарантувати лише форматом JSON.

## 11. Покажіть у трасі Langfuse крок, вхід, рішення, дію і результат одного кроку агента.

На прикладі траси `checks-Z3` перший крок — це звернення до моделі із завданням вибрати ноутбук для навчання та розрахувати розстрочку.

Входом є запит користувача.

Рішенням є вибір інструмента `search_laptops`.

Дією є виклик `call_tool` з аргументом `{"query":"навчання"}`.

Результатом є відповідь `StudyNova 14 | StudyNova 15`.

На наступних кроках агент отримує ціну ноутбука, виконує розрахунок, отримує помилку `meaning` і повторює виклик із правильними аргументами.
