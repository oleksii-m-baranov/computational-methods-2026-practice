# 5. Класи аргументів трьох інструментів

Для перевірки аргументів створено файл `arguments.py`.

Використано бібліотеку Pydantic, яка дозволяє задавати типи, обов'язкові поля та допустимі межі значень.

## 5.1. Код файлу `arguments.py`

```python
from pydantic import BaseModel, Field, ConfigDict


class SearchLaptopsArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    query: str = Field(
        min_length=1,
        description="Текстовий запит для пошуку ноутбуків"
    )


class LaptopInfoArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    model: str = Field(
        min_length=1,
        description="Точна назва моделі ноутбука"
    )


class CalcInstallmentArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    price: float = Field(
        gt=0,
        description="Вартість ноутбука у гривнях"
    )

    months: int = Field(
        ge=1,
        le=60,
        description="Кількість місяців розстрочки"
    )

    overpay_percent: float = Field(
        ge=0,
        le=100,
        description="Відсоток переплати"
    )


ARGUMENT_MODELS = {
    "search_laptops": SearchLaptopsArgs,
    "laptop_info": LaptopInfoArgs,
    "calc_installment": CalcInstallmentArgs
}
```

## 5.2. Пояснення роботи класів

Клас `SearchLaptopsArgs` перевіряє, щоб аргумент `query` був непорожнім текстовим рядком.

Клас `LaptopInfoArgs` перевіряє наявність назви моделі ноутбука.

Клас `CalcInstallmentArgs` перевіряє числові параметри:

- `price` — ціна повинна бути більшою за нуль;
- `months` — кількість місяців від 1 до 60;
- `overpay_percent` — відсоток переплати від 0 до 100.

Параметр:

```python
model_config = ConfigDict(extra="forbid")
```

забороняє передавати невідомі поля.

Це дозволяє виявляти неправильні аргументи ще до виконання інструмента.

## 6.1. Перевірка змісту

Перевірка схеми не завжди гарантує правильність аргументів.

Наприклад:

```python
laptop_info({"model": "UnknownLaptop999"})
```

Цей виклик має правильний формат, але моделі `UnknownLaptop999` немає в довіднику.

Тому диспетчер повинен повернути помилку рівня `meaning`.

Це дозволяє виявляти ситуації, коли аргументи правильні за типом, але неправильні за змістом.

# 7. Реалізація ланцюжка перевірок

У файлі `dispatcher.py` реалізовано послідовну перевірку викликів інструментів.

Основні рівні:

1. `name` — перевірка існування інструмента.
2. `permission` — перевірка дозволу.
3. `syntax` — перевірка синтаксису JSON.
4. `schema` — перевірка аргументів через Pydantic.
5. `meaning` — перевірка змісту.
6. `tool` — помилка виконання інструмента.
7. `ok` — успішне виконання.

## Таблиця 2 — Перевірка ланцюжка перевірок

| Що перевіряємо | Виклик | Рівень | Повідомлення для моделі |
|---|---|---|---|
| Зламаний JSON | `search_laptops({"query":` | `syntax` | Помилка синтаксису JSON. Необхідно виправити формат аргументів |
| Неправильний тип | `search_laptops({"query":123})` | `schema` | Поле `query` повинно бути текстовим рядком |
| Відсутнє обов'язкове поле | `search_laptops({})` | `schema` | Необхідно додати поле `query` |
| Зайве поле | `search_laptops({"query":"навчання","extra":1})` | `schema` | Поле `extra` не дозволене. Необхідно видалити його |
| Неіснуючий інструмент | `unknown_tool({})` | `name` | Інструмент не знайдено. Використайте доступний інструмент |
| Заборонений інструмент | `place_order({"model":"StudyNova 14"})` | `permission` | Оформлення замовлення заборонено |
| Неіснуюча модель | `laptop_info({"model":"UnknownLaptop999"})` | `meaning` | Модель відсутня в довіднику. Необхідно використати допустиму назву |
| Значення поза межами | `calc_installment({"price":22000,"months":100,"overpay_percent":10})` | `schema` | Кількість місяців повинна бути від 1 до 60 |

# 8. Реалізація повторних спроб

Для запобігання нескінченному повторенню неправильних викликів реалізовано ліміт помилок.

У файлі конфігурації встановлено:

```python
MAX_RETRIES = 2
```

Якщо модель отримує помилку, її лічильник збільшується.

Якщо наступний виклик успішний, лічильник обнуляється.

Приклад логіки:

```python
if model_failed:
    retries += 1

    if retries > config.MAX_RETRIES:
        logger.error(
            "СТОП: перевищено ліміт помилок моделі"
        )
        return None

elif tool_succeeded:
    retries = 0
```

Повідомлення про помилку передається моделі, щоб вона могла сформувати виправлений виклик.

Таким чином, повторна спроба виконується в основному циклі агента.

# 10. Аналіз трасування Langfuse

Langfuse дозволяє досліджувати послідовність дій агента.

Для кожного кроку можна визначити:

- вхід;
- рішення;
- дію;
- результат;
- кількість токенів;
- час виконання.

## 10.1. Структура події

```text
Крок агента
    |
    v
Вхідні повідомлення
    |
    v
Рішення мовної моделі
    |
    v
Виклик інструмента
    |
    v
Результат виконання
```

**Крок** — одна ітерація роботи агента.

**Вхід** — завдання користувача та історія повідомлень.

**Рішення** — вибір інструмента та формування аргументів.

**Дія** — виконання `call_tool`.

**Результат** — відповідь інструмента або повідомлення про помилку.

# 15. Питання для захисту

## 1. На які три рівні поділяють помилки у виклику інструмента? Наведіть приклад кожної зі свого прогону або з табл. 2.

Помилки можна поділити на помилки вибору інструмента, помилки аргументів і помилки виконання. Наприклад, `unknown_tool` — помилка назви інструмента, `{"query":123}` — помилка схеми, а збій під час виконання функції — помилка рівня `tool`.

## 2. Чому `call_tool` перевіряє існування і дозвіл інструмента раніше за аргументи?

Спочатку потрібно переконатися, що інструмент існує та його дозволено викликати. Немає сенсу перевіряти аргументи інструмента, який не існує або заборонений політикою доступу.

## 3. Що станеться, якщо в класі Pydantic не вказати `extra="forbid"`?

За типової конфігурації Pydantic зайві поля можуть ігноруватися. Це означає, що модель зможе передати невідомий аргумент, а перевірка схеми не повідомить про нього як про помилку.

## 4. Навіщо генерувати описи інструментів з класів Pydantic, а не писати їх вручну, як у лабораторній роботі № 2?

Генерування схем із Pydantic дозволяє уникнути розбіжностей між описом інструмента та правилами перевірки в коді. Якщо змінити клас аргументів, відповідна JSON-схема може бути оновлена автоматично.

## 5. Чому недостатньо просто не передавати моделі заборонений інструмент у `SCHEMAS`?

Модель може сформувати неправильну назву інструмента або спробувати викликати заборонену дію. Тому перевірка дозволів повинна виконуватися безпосередньо в диспетчері, незалежно від того, які інструменти були показані моделі.

## 6. Які правила змісту ви перенесли в класи, а які лишили в `check_meaning`? Чому?

У Pydantic-класи перенесено перевірки типів, обов'язкових полів і числових меж. У `check_meaning` залишено перевірку існування моделі в довіднику, оскільки вона залежить від фактичних даних CSV-файлу.

## 7. Чим помилка моделі відрізняється від помилки інструмента та чому повідомлення для них різні?

Помилка моделі виникає, коли вона неправильно вибирає інструмент або формує його аргументи. Помилка інструмента виникає під час виконання функції, тому моделі потрібно повідомити не про неправильний формат аргументів, а про проблему виконання.

## 8. Що ловить `check_response` і чому без цієї перевірки такий випадок виглядав як «не викликав інструмент»?

`check_response` перевіряє, чи відповідь моделі має очікувану структуру та чи не містить помилок формату або обмежень довжини. Без цієї перевірки некоректна відповідь могла б сприйматися як звичайна відсутність виклику інструмента.

## 9. Покажіть у коді, де відбувається повторна спроба. Чому для неї не потрібен окремий механізм і чому повторна спроба без пояснення помилки найчастіше не допомагає?

Повторна спроба відбувається в основному циклі `run_agent`, коли після помилки модель отримує нове повідомлення й виконується наступна ітерація. Окремий механізм не потрібен, оскільки цикл уже підтримує повторні звернення; без пояснення помилки модель може знову сформувати той самий неправильний виклик.

## 10. Чим запобігання помилкам на сервері відрізняється від виявлення в коді? Чому навіть зі structured output перевірку в коді не прибирають?

Structured output обмежує формат відповіді ще під час генерації, а перевірки в коді аналізують уже отримані дані. Навіть зі structured output потрібно перевіряти дозволи, існування значень у довіднику та інші правила, які неможливо гарантувати лише форматом JSON.

## 11. Покажіть у трасі Langfuse крок, вхід, рішення, дію і результат одного кроку агента.

На прикладі траси `recovery-test` перший крок — це звернення до моделі із завданням перевірити ноутбук. Входом є запит користувача, рішенням — вибір `laptop_info` з аргументом `UnknownLaptop999`, дією — виклик `call_tool`, а результатом — помилка `meaning`, після якої агент змінює свою поведінку.
