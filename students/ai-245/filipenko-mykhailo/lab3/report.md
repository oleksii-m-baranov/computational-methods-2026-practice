# 5. Класи аргументів трьох інструментів

Для перевірки аргументів створено файл `arguments.py`.

Pydantic дозволяє контролювати типи даних, обов'язкові поля, числові межі та наявність зайвих аргументів.

## 5.1. Реалізація arguments.py

```python
from pydantic import BaseModel, Field, ConfigDict


class SearchLaptopsArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    query: str = Field(min_length=1)


class LaptopInfoArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    model: str = Field(min_length=1)


class CalcInstallmentArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    price: float = Field(gt=0)

    months: int = Field(ge=1, le=60)

    overpay_percent: float = Field(
        ge=0,
        le=100
    )
```

## 5.2. Пояснення коду

Клас `SearchLaptopsArgs` перевіряє, щоб аргумент `query` був непорожнім текстовим рядком.

Клас `LaptopInfoArgs` вимагає передавання назви моделі через поле `model`.

Клас `CalcInstallmentArgs` перевіряє:

- `price` — додатне число;
- `months` — ціле число від 1 до 60;
- `overpay_percent` — число від 0 до 100.

Конструкція:

```python
model_config = ConfigDict(extra="forbid")
```

забороняє передавати невідомі поля.

Це важливо, оскільки мовна модель може сформувати аргументи, яких немає в описі інструмента.

# 6. Правила перевірки змісту

Не всі помилки можна виявити за допомогою перевірки типів даних.

Наприклад, назва `UnknownLaptop999` є допустимим текстовим значенням, однак такої моделі немає в довіднику.

Аналогічно ціна 8000 грн є додатним числом, але не відповідає підтвердженій ціні ноутбука StudyNova 14.

Для таких випадків реалізовано додаткові перевірки змісту.

## Таблиця 1 — Правила перевірки аргументів

| Аргумент | Правило | Де записано | Звідки взято межу |
|---|---|---|---|
| `search_laptops.query` | Непорожній текстовий рядок | `SearchLaptopsArgs` | Вимога до пошукового запиту |
| `laptop_info.model` | Непорожній текстовий рядок | `LaptopInfoArgs` | Обов'язкове поле |
| `laptop_info.model` | Модель існує в довіднику | `check_meaning` | `data/laptops.csv` |
| `calc_installment.price` | Ціна більше 0 | `CalcInstallmentArgs` | Додатна ціна покупки |
| `calc_installment.price` | Ціна попередньо підтверджена | `check_meaning` | Результат `laptop_info` |
| `calc_installment.price` | Ціна збігається з підтвердженою | `check_meaning` | Контекст агента |
| `calc_installment.months` | Від 1 до 60 | `CalcInstallmentArgs` | Межі проєкту |
| `calc_installment.overpay_percent` | Від 0 до 100 | `CalcInstallmentArgs` | Межі переплати |
| Назва інструмента | Інструмент існує | `dispatcher.py` | Перелік інструментів |
| `place_order` | Виклик заборонений | `dispatcher.py` | Вимога варіанта №9 |

## 6.1. Перевірка моделі ноутбука

Під час виклику `laptop_info` система перевіряє, чи існує передана назва моделі в локальному довіднику.

Наприклад:

```python
laptop_info({
    "model": "UnknownLaptop999"
})
```

Такий виклик відповідає вимогам Pydantic, але не проходить семантичну перевірку.

Диспетчер повертає помилку рівня `meaning`.

## 6.2. Перевірка ціни

Для розрахунку розстрочки необхідно спочатку отримати фактичну ціну ноутбука через `laptop_info`.

У контексті агента зберігається підтверджена ціна:

```python
verified_price = context.get("verified_price")
```

Якщо підтверджена ціна відсутня, виклик `calc_installment` відхиляється.

Якщо передана ціна відрізняється від підтвердженої, система також повертає помилку.

Приклад логіки перевірки:

```python
verified_price = context.get("verified_price")

if verified_price is None:
    return False, (
        "Перед розрахунком розстрочки необхідно "
        "отримати ціну через laptop_info."
    )

if abs(float(price) - float(verified_price)) > 0.01:
    return False, (
        "Передана ціна не відповідає "
        "підтвердженій ціні ноутбука."
    )
```

Завдяки цьому перевіряється не тільки формат аргументів, а й відповідність даних реальним результатам інструментів.

# 7. Реалізація ланцюжка перевірок

У файлі `dispatcher.py` реалізовано перевірку викликів інструментів перед їхнім виконанням.

Послідовність перевірок:

1. `name` — чи існує інструмент;
2. `permission` — чи дозволено його використовувати;
3. `syntax` — чи правильно сформовано JSON;
4. `schema` — чи відповідають аргументи Pydantic-схемі;
5. `meaning` — чи відповідають аргументи предметній області;
6. `tool` — чи не виникла помилка під час виконання функції;
7. `ok` — успішне виконання.

Така послідовність дозволяє відхиляти некоректні виклики до їхнього фактичного виконання.

## Таблиця 2 — Перевірка ланцюжка перевірок

| Що перевіряємо | Виклик | Рівень | Повідомлення для моделі |
|---|---|---|---|
| Зламаний JSON | `search_laptops({"query":` | `syntax` | Некоректний JSON |
| Неправильний тип | `search_laptops({"query":123})` | `schema` | Поле `query` повинно бути рядком |
| Відсутнє поле | `search_laptops({})` | `schema` | Необхідно додати поле `query` |
| Зайве поле | `search_laptops({"query":"навчання","extra":1})` | `schema` | Поле `extra` не дозволене |
| Неіснуючий інструмент | `unknown_tool({})` | `name` | Інструмент не знайдено |
| Заборонений інструмент | `place_order({"model":"StudyNova 14"})` | `permission` | Оформлення замовлення заборонено |
| Неіснуюча модель | `laptop_info({"model":"UnknownLaptop999"})` | `meaning` | Модель відсутня в довіднику |
| Значення поза межами | `calc_installment({"price":22000,"months":100,"overpay_percent":10})` | `schema` | Кількість місяців повинна бути від 1 до 60 |
| Непідтверджена ціна | `calc_installment({"price":22000,"months":6,"overpay_percent":10})` | `meaning` | Спочатку отримати ціну через `laptop_info` |
| Невідповідність ціни | `calc_installment({"price":8000,"months":6,"overpay_percent":10})` | `meaning` | Ціна не відповідає підтвердженій |
| Правильна ціна | `calc_installment({"price":22000,"months":6,"overpay_percent":10})` | `ok` | Розрахунок виконано |

# 8. Реалізація повторних спроб

Для підвищення надійності агента реалізовано механізм повторних спроб.

Якщо диспетчер виявляє помилку, він повертає мовній моделі повідомлення з поясненням.

Після цього модель отримує можливість сформувати виправлений виклик.

У конфігурації використано:

```python
MAX_RETRIES = 3
```

Ліміт повторних помилок запобігає нескінченному повторенню некоректних дій.

## 8.1. Виявлення помилки в задачі Z3

У режимі Checks агент отримав завдання:

```text
Порадь ноутбук для навчання і скажи,
скільки платити на місяць при розстрочці
на 6 місяців з переплатою 10%
```

На першому кроці агент викликав:

```python
search_laptops({
    "query": "навчання"
```

Оскільки підтверджена ціна ще не була записана в контексті, розрахунок розстрочки було відхилено.

У логах зафіксовано:


## 8.2. Успішне виправлення

Після повідомлення про помилку агент повторно отримав інформацію про ноутбук.

```python
laptop_info({
    "model": "StudyNova 14"
})
```

Результат:

```text
Ціна: 22000 грн
На складі: 5 шт.
Гарантія: 24 міс.
```

Після підтвердження ціни агент викликав:

```python
calc_installment({
    "price": 22000,
    "months": 6,
    "overpay_percent": 10
})
```

Результат:

```text
4033.33 грн на місяць
Усього 24200.00 грн
```

Перевірка:

```text
22000 × 1.10 = 24200 грн
24200 ÷ 6 = 4033.33 грн
```

Отже, правильний щомісячний платіж становить 4033,33 грн, а загальна сума розстрочки — 24200 грн.

# 10. Аналіз трасування Langfuse

Langfuse дозволяє детально дослідити роботу агента.

У трасах можна переглядати послідовність викликів моделі, аргументи інструментів, результати виконання, помилки перевірок, кількість токенів і тривалість операцій.

## 10.1. Структура події

Кожну подію агента можна розділити на п'ять частин:

1. **Крок** — виклик мовної моделі.
2. **Вхід** — історія повідомлень і запит користувача.
3. **Рішення** — вибір інструмента та аргументів.
4. **Дія** — виконання `call_tool`.
5. **Результат** — рівень перевірки та відповідь інструмента.

Приклад:

```text
КРОК:
agent_step

ВХІД:
Порадь ноутбук для навчання

РІШЕННЯ:
search_laptops({"query":"навчання"})

ДІЯ:
call_tool

РЕЗУЛЬТАТ:
ok
StudyNova 14 | StudyNova 15
```

Модель передала допустиме додатне число, яке відповідало вимогам формату аргументів.

Тому звичайна перевірка типу та числових меж не могла виявити невідповідність.

Помилка виникла через використання неправильної ціни, а не через неправильну математичну формулу.

У режимі Baseline семантична перевірка відповідності ціни не застосовувалася.

Аналіз показав, що формально правильні аргументи можуть містити неправильні значення.

# 15. Питання для захисту

## 1. На які три рівні поділяють помилки у виклику інструмента? Наведіть приклад кожної зі свого прогону або з табл. 2.

Помилки можна поділити на помилки вибору інструмента, помилки аргументів і помилки виконання. Наприклад, виклик `unknown_tool` є помилкою назви інструмента, `{"query":123}` — помилкою схеми аргументів, а виняток під час виконання функції належить до рівня `tool`.

## 2. Чому `call_tool` перевіряє існування і дозвіл інструмента раніше за аргументи?

Спочатку потрібно переконатися, що інструмент існує та його використання дозволене. Немає сенсу перевіряти аргументи функції, яку неможливо або заборонено викликати.

## 3. Що станеться, якщо в класі Pydantic не вказати `extra="forbid"`?

За типової конфігурації Pydantic зайві поля можуть ігноруватися. У такому випадку модель може передати невідомий аргумент, а перевірка схеми не повідомить про нього як про помилку.

## 4. Навіщо генерувати описи інструментів з класів Pydantic, а не писати їх вручну, як у лабораторній роботі №2?

Генерування описів із Pydantic дозволяє уникнути розбіжностей між схемою аргументів і правилами перевірки в коді. Якщо змінити клас аргументів, JSON-схему можна оновити автоматично.

## 5. Чому недостатньо просто не передавати моделі заборонений інструмент у `SCHEMAS`?

Модель може сформувати назву забороненого інструмента навіть тоді, коли його немає в доступних схемах. Тому перевірка дозволів повинна виконуватися безпосередньо в диспетчері перед запуском функції.

## 6. Які правила змісту ви перенесли в класи, а які лишили в `check_meaning`? Чому?

У Pydantic-класи перенесено перевірки типів, обов'язкових полів і числових меж. У `check_meaning` залишено перевірку існування моделі в довіднику та відповідності ціни підтвердженим даним, оскільки ці правила залежать від CSV-файлу й контексту агента.

## 7. Чим помилка моделі відрізняється від помилки інструмента та чому повідомлення для них різні?

Помилка моделі виникає, коли вона неправильно вибирає інструмент або формує його аргументи. Помилка інструмента виникає під час виконання функції, тому повідомлення повинно пояснювати проблему виконання, а не лише неправильний формат аргументів.

## 8. Що ловить `check_response` і чому без цієї перевірки такий випадок виглядав як «не викликав інструмент»?

`check_response` перевіряє структуру відповіді моделі та виявляє некоректні або порожні відповіді, а також порушення встановлених обмежень. Без такої перевірки зламаний виклик міг би помилково трактуватися як звичайна відсутність виклику інструмента.

## 9. Покажіть у коді, де відбувається повторна спроба. Чому для неї не потрібен окремий механізм і чому повторна спроба без пояснення помилки найчастіше не допомагає?

Повторна спроба відбувається в основному циклі агента після повернення повідомлення про помилку. Окремий механізм не потрібен, оскільки цикл уже підтримує повторні звернення до моделі. Без пояснення причини помилки модель може повторити той самий неправильний виклик.

## 10. Чим запобігання помилкам на сервері відрізняється від виявлення в коді? Чому навіть зі structured output перевірку в коді не прибирають?

Structured output обмежує формат відповіді під час генерації, а перевірки в коді аналізують уже отримані дані. Навіть за наявності structured output потрібно перевіряти дозволи, існування значень у довіднику та інші правила предметної області.

## 11. Покажіть у трасі Langfuse крок, вхід, рішення, дію і результат одного кроку агента.

На прикладі траси Z3 кроком є вузол `agent_step`, а входом — запит користувача про ноутбук для навчання та розстрочку. Рішенням моделі є виклик `search_laptops` з аргументом `{"query":"навчання"}`. Дією є вузол `call_tool`, а результатом — рівень `ok` і список моделей `StudyNova 14 | StudyNova 15`.
