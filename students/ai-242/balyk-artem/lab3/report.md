# 3. Класи аргументів інструментів

`arguments.py`

```python
"""Класи аргументів інструментів."""

from pydantic import BaseModel, ConfigDict, Field


class SearchRecipesArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    query: str = Field(
        min_length=1,
        description=(
            "Інгредієнт, тип страви або спосіб приготування: "
            "одне-два слова українською, наприклад рис, суп або духовка."
        )
    )


class ProductInfoArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    product: str = Field(
        min_length=1,
        description=(
            "Назва продукту в називному відмінку однини, "
            "у нижньому регістрі, як у довіднику, "
            "наприклад рис або морква."
        )
    )


class ScaleAmountArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")

    amount: float = Field(
        gt=0,
        description=(
            "Початкова кількість одного інгредієнта "
            "в оригінальному рецепті."
        )
    )

    base_servings: float = Field(
        gt=0,
        description=(
            "Кількість порцій, на яку розрахований "
            "оригінальний рецепт. Має бути більшою за нуль."
        )
    )

    target_servings: float = Field(
        gt=0,
        description=(
            "Кількість порцій, для якої потрібно "
            "перерахувати інгредієнт."
        )
    )


ARGS = {
    "search_recipes": SearchRecipesArgs,
    "product_info": ProductInfoArgs,
    "scale_amount": ScaleAmountArgs,
}
```

У всіх класах використовується `ConfigDict(extra="forbid")`, щоб заборонити передавання аргументів, які не передбачені схемою.

Для числових аргументів інструмента `scale_amount` встановлено обмеження `gt=0`, яке не дозволяє передавати нульові або від'ємні значення.

# 7. Аналіз трас у Langfuse

## 7.1. Структура події

Подію в трасі можна розділити на п'ять частин:

1. **Крок** — вузол виклику моделі в дереві траси.
2. **Вхід** — історія повідомлень, передана моделі.
3. **Рішення** — відповідь моделі з назвою інструмента та аргументами.
4. **Дія** — вузол `call_tool`, який отримує назву інструмента й аргументи.
5. **Результат** — вихід `call_tool`, що містить рівень перевірки та текст результату.

## 4. Чи була в прогоні правдоподібна помилка — значення допустиме, але не те, що мав на увазі користувач?

Так. Під час додаткового тестування structured output модель отримала запит про перерахунок 300 г рису з 4 на 10 порцій, але повернула `amount = 10` замість `amount = 300`.

JSON пройшов перевірку Pydantic, оскільки значення 10 є допустимим додатним числом. Перевірка структури не визначає, чи правильно модель зрозуміла зміст запиту.

## 5. Які поламки перевірки не лікують у принципі та чому?

Перевірки аргументів не гарантують правильного розуміння наміру користувача та не виявляють усіх семантично неправильних, але формально допустимих значень. Також вони не гарантують, що модель використає результат інструмента у кінцевій відповіді. Для цього потрібні додаткові механізми контролю якості відповіді та точніші інструкції моделі.

## 6. Скільки додаткових викликів моделі пішло на виправлення помилок? Чи виправдана така ціна надійності?

На додатковому прикладі з неіснуючим продуктом, модель врахувала повідомлення про помилку і передалі користувачу. Це те ж саме, що й якби вона отримала відповідь і передалі її і довше за просто вигадану неіснуючу відповідь.

## 7. Візьміть найдовшу задачу. Що в ній легше побачити в трасі Langfuse, а що — у текстовому лозі?

У текстовому лозі зручно переглядати послідовність подій і порівнювати текстові результати. На довгих задачах текстовий лог стає важко читати через накопичення повідомлень, повторних викликів і аргументів. В Langfuse набагато зручніше переглядати кожен виклик і крок і порівнювати багато викликів у графічному форматі та форматі таблиці.

# 9. Додаткове завдання — Structured Output

Для перевірки structured output було створено файл `structured_demo.py`.

У ньому використовується Pydantic-схема інструмента `scale_amount`, яка передається моделі через параметр `response_format` з типом `json_schema`.

Після отримання відповіді виконується додаткова перевірка методом `model_validate_json()`.

```text
Рецепт містить 300 г рису на 4 порції. Потрібно приготувати 10 порцій. Сформуй аргументи для перерахунку.
```

Під час тестування модель повернула:

```json
{
  "amount": 10,
  "base_servings": 4,
  "target_servings": 10
}
```

Pydantic успішно перевірив результат і сформував об'єкт:

```text
amount=10.0 base_servings=4.0 target_servings=10.0
```

Проте в початковому запиті йшлося про 300 г рису, тому правильним значенням `amount` було 300, а не 10.

Цей експеримент показав, що модель підтримує використаний режим structured output, а JSON відповідає заданій структурі. Водночас structured output не гарантує правильності змісту аргументів.

Ще одна перевірка, яка спровокує помилку:

```text
Рецепт містить 300 г рису на 4 порції. Потрібно приготувати 0 порцій. Сформуй аргументи для перерахунку.
```

**Висновок додаткового завдання:** повністю прибирати перевірки Pydantic і семантичні перевірки недоцільно. Structured output допомагає обмежити формат генерації, але не замінює перевірку правильності даних.

Під час лабораторної роботи було вдосконалено локального кулінарного LLM-агента: створено Pydantic-схеми аргументів, реалізовано семантичні перевірки, контроль доступу до інструментів та обробку помилок. Також налаштовано моніторинг роботи агента за допомогою Langfuse.

Проблеми залишилися з пошуком страв, використанням результатів інструментів та визначенням наміру користувача.

Порівняння показало, що кількість викликів моделі та використаних токенів не змінилася: для кожного завдання виконано 2 виклики, а витрати становили від 1997 до 2066 токенів. Час виконання також залишився практично незмінним. Отже, впроваджені перевірки не спричинили помітного збільшення обчислювальних витрат, але й не покращили точність виконання тестових завдань.

Найбільший ефект дало впровадження Pydantic-валідації та семантичних перевірок, оскільки вони дозволили виявляти некоректні аргументи й заборонені дії до виконання інструментів. Усі 8 тестів диспетчера пройшли успішно. Додатковий експеримент зі structured output показав, що відповідність JSON-схемі не гарантує правильності значень, тому перевірку Pydantic необхідно зберегти.

Надалі варто покращити пошук з урахуванням словоформ, вибір інструментів відповідно до наміру користувача та використання результатів інструментів у фінальних відповідях. Також доцільно розширити набір тестів для перевірки надійності агента в різних ситуаціях.
