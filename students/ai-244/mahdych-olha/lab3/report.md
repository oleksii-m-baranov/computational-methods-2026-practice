## 3. Класи аргументів інструментів

У `arguments.py` створено класи Pydantic. `extra="forbid"` забороняє невідомі поля, а поля без значень за замовчуванням обов’язкові. Межі `gt=0` відхиляють нульові та від’ємні кількості.

```python
from pydantic import BaseModel, ConfigDict, Field

class SearchRecipesArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    query: str = Field(description="Інгредієнт, тип страви або спосіб приготування: одне-два слова українською, не все питання користувача.")

class ProductInfoArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    product: str = Field(description="Назва продукту в називному відмінку однини, як у довіднику.")

class ScaleAmountArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    amount: float = Field(gt=0, allow_inf_nan=False, description="Кількість інгредієнта в оригінальному рецепті.")
    base_servings: float = Field(gt=0, allow_inf_nan=False, description="Кількість порцій в оригінальному рецепті.")
    target_servings: float = Field(gt=0, allow_inf_nan=False, description="Потрібна кількість порцій.")

ARGS = {"search_recipes": SearchRecipesArgs, "product_info": ProductInfoArgs, "scale_amount": ScaleAmountArgs}
```

`schemas.py` отримує описи параметрів із цих класів через `model_json_schema()`. Так модель і перевірка в коді використовують однакові правила.

## 4. Правила змісту

| Аргумент | Правило | Де записано | Звідки взято межу або правило |
|---|---|---|---|
| `search_recipes.query` | Обов’язковий рядок. | `SearchRecipesArgs` | Опис інструмента у варіанті 2 лабораторної № 2. |
| `product_info.product` | Обов’язковий рядок; назва має бути в довіднику. | Тип і обов’язковість — `ProductInfoArgs`; наявність — `check_meaning` | Стовпець `product` у CSV та логіка пошуку `product_info`. |
| `scale_amount.amount` | Скінченне число більше нуля. | `ScaleAmountArgs` | Кількість інгредієнта в задачі — 300 г; нульова кількість для перерахунку не використовується. |
| `scale_amount.base_servings` | Скінченне число більше нуля. | `ScaleAmountArgs` | Функція повертає помилку для `base_servings <= 0`. |
| `scale_amount.target_servings` | Скінченне число більше нуля. | `ScaleAmountArgs` | Потрібна кількість порцій має бути додатною. |

`check_meaning` перевіряє назву продукту без урахування регістру. Для продукту, якого немає у CSV (у наборі це лимон), інструмент не запускається, а модель отримує пояснення та вказівку перевірити довідник.

## 5. Перевірка ланцюжка диспетчера

Диспетчер перевіряє виклик послідовно. Назва та дозвіл перевіряються до аргументів, бо для невідомого або забороненого інструмента перевіряти аргументи немає сенсу.

**Таблиця 1 — Порядок перевірок диспетчера**

| Порядок | Перевірка | Рівень у лозі | Тип помилки |
|---:|---|---|---|
| 1 | Чи існує інструмент | `name` | Схема |
| 2 | Чи дозволено викликати інструмент | `permission` | Зміст |
| 3 | Чи розбираються аргументи як JSON | `syntax` | Синтаксис |
| 4 | Чи відповідають аргументи класу | `schema` | Схема та правила класу |
| 5 | Чи мають значення сенс для даних | `meaning` | Зміст |
| 6 | Чи спрацював інструмент | `tool` | Помилка інструмента |

У `test_checks.py` додатково перевірено всі вісім типів відмов із методички та один валідний виклик. **Усі 9 випадків пройшли.**

**Таблиця 2 — Перевірка ланцюжка перевірок**

| Випадок | Приклад виклику | Рівень | Що повернув диспетчер |
|---|---|---|---|
| Зламаний JSON | `product_info`, `{"product":"рис"` | `syntax` | Повідомлення, що JSON неправильний, і прохання виправити аргументи. |
| Неправильний тип | `scale_amount`, `amount="сто"` | `schema` | Поле `amount` має бути числом. |
| Відсутнє поле | `product_info`, `{}` | `schema` | Обов’язкове поле `product` відсутнє. |
| Зайве поле | `product_info`, `{"product":"рис","x":1}` | `schema` | Поле `x` заборонене. |
| Невідомий інструмент | `delete_all`, `{}` | `name` | Перелічено доступні інструменти. |
| Заборонена дія | `place_order`, `{"product":"рис"}` | `permission` | Інструмент недоступний; його не слід викликати повторно. |
| Немає продукту в довіднику | `product_info`, `{"product":"лимон"}` | `meaning` | Продукт відсутній; назву запропоновано перевірити у CSV. |
| Поза межею | `scale_amount`, `base_servings=0` | `schema` | Кількість порцій має бути більшою за нуль. |
| Валідне обчислення | `scale_amount`, `300, 4, 10` | `ok` | Результат `750.0`. |

Спочатку перевіряються назва та дозвіл інструмента, потім JSON і схема, зміст і виконання. Помилка інструмента має рівень `tool`, окремий від помилок моделі: агент не може виправити внутрішній збій функції.

## 8. Відповіді на питання

1. **Які поламки зникли або зменшилися після впровадження перевірок? Які лишилися?** У стандартному прогоні перевірки аргументів не спрацьовували, отже цей прогін не засвідчив зменшення таких помилок. Вигадане число Z2 залишилося, а після перевірок у Z1 з’явилася вигадана назва страви (таблиці 3–5).

2. **На якому рівні модель помилялася найчастіше? Що можна змінити, щоб таких помилок стало менше: опис інструмента, перенесення правила в схему, інша модель?** У п’яти основних задачах рівнів помилки не було; у додатковій перевірці E1 один раз виник `schema`, і модель виправилася. Варто чіткіше вимагати використання довідника для калорійності; для виявлення вигаданих чисел у фінальній відповіді потрібна окрема перевірка її змісту.

3. **Чи траплялися відмови після ліміту помилок? Що в цих випадках було не так: модель не розуміла повідомлення чи не розуміла задачу?** Відмов після перевищення `MAX_RETRIES=2` не було. У E1 сталася одна помилка, після якої модель виправила аргумент і завершила задачу.

4. **Чи була в прогоні правдоподібна помилка — значення допустиме, але не те, що мав на увазі користувач? Чому жодна перевірка її не зловила?** Так, 373 ккал у Z2 виглядає правдоподібно, але довідник містить 344 ккал на 100 г. Pydantic перевіряв аргументи інструментів, а не звичайний текст відповіді.

5. **Які поламки перевірки не лікують у принципі та чому?** Вони не гарантують правдивість фінальної відповіді, не змушують модель сама викликати потрібний інструмент і не визначають, чи точно модель передала намір користувача. Для цього потрібні перевірки змісту відповіді та додаткові правила програми.

6. **Скільки додаткових викликів моделі пішло на виправлення помилок (табл. 6)? Чи виправдана така ціна надійності?** У п’яти стандартних задачах додаткових викликів не було: по дев’ять до й після. У окремій трасі E1 повторний виклик виправив некоректну кількість порцій; для цього перевірочного прикладу додатковий виклик був корисним.

7. **Візьміть найдовшу задачу. Що в ній легше побачити в трасі Langfuse, а що — у текстовому лозі? Чому на довгих задачах текстовий лог стає важко читати?** Найдовшою за часом у базовому прогоні була Z1 — 25.239 с, два кроки моделі. Langfuse наочно показує дерево подій і тривалість, а текстовий лог послідовно показує аргументи та відповіді; довгі історії й повторені повідомлення роблять його об’ємним.

## 10. Висновок

Перевірки Pydantic і змісту відхилили всі вісім навмисно помилкових прикладів диспетчера, а правильний розрахунок пройшов. У окремій трасі E1 повідомлення `schema` супроводжувалося виправленим повторним викликом.

На п’яти основних задачах загальна точність не змінилася: 3 із 5 до і після. Найважливіше наступне покращення — перевіряти, чи фінальні числа взяті з довідника, та чи не змінила модель назви, отримані інструментом. Висновки обмежені цими п’ятьма задачами й проведеними прогонами.
