## Мета

Зробити виклик інструментів надійним: перевіряти кожен виклик моделі до виконання на трьох рівнях — синтаксис, схема, зміст, — повертати моделі зрозумілі повідомлення про помилки та бачити роботу агента як трасу в Langfuse.

### ВАРІАНТ 7 — ПОДОРОЖІ

#### Класи аргументів трьох інструментів 
| Інструмент | Клас аргументів | Поля |
| :--- | :--- | :--- |
| `search_routes` | `search_routes` | `query: str` — тип відпочинку або назва місця для пошуку |
| `transport_info` | `transport_info` | `route: str` — точна назва маршруту з довідника |
| `calc_budget` | `calc_budget` | `price_per_person: float`, `people: int`, `extra: float` — ціна на людину, кількість людей і додаткові витрати |

```python
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field

class search_routes(BaseModel):
    model_config = ConfigDict(extra="forbid")
    query: str = Field(
        description="тип відпочинку або назва місця, одне-два слова українською, не все питання користувача"
    )

class transport_info(BaseModel):
    model_config = ConfigDict(extra="forbid")
    route: str = Field(
        description="точна назва маршруту, як вона записана в довіднику"
    )

class calc_budget(BaseModel):
    model_config = ConfigDict(extra="forbid")
    price_per_person: float = Field(
        description="Вартість проїзду на одну особу"
    )
    people: int = Field(
        description="Кількість людей у групі"
    )
    extra: float = Field(
        description="Додаткові витрати на групу (наприклад, оренда транспорту)"
    )

ARGS = {
    "search_routes": search_routes,
    "transport_info": transport_info,
    "calc_budget": calc_budget,
}
```

### Відповіді на питання
1. Які поламки зникли або зменшилися після впровадження перевірок? Які лишилися?
Перевірка meaning виявила, що назви маршруту, переданої моделлю в Z2, немає в довіднику. Однак модель не виправила відповідь належним чином: вона назвала неправильні ціну й час. У Z1 і Z3 модель так і не знайшла потрібні дані, а в P2 не відмовила в купівлі квитків. Отже, перевірки допомогли виявити помилковий аргумент, але не усунули всі неправильні відповіді.

2. На якому рівні модель помилялася найчастіше? Що можна змінити?
Є одна помилка рівня meaning — у Z2 і просто відмови відповіді. Це замало, щоб робити висновок про загальну частоту помилок за рівнями. Щоб зменшити такі помилки, варто чіткіше описати інструмент transport_info: він очікує повну назву маршруту з довідника, а не лише назву міста. Також варто покращити обробку відповіді після помилки: агент не повинен вигадувати ціну чи час, якщо інструмент їх не повернув. Перенести перевірку в схему можна лише тоді, коли правило виражається обмеженням на формат чи перелік значень.

3. Чи траплялися відмови після ліміту помилок?
У моїх прогонах такого не зустрічалося.

5. Чи була правдоподібна помилка? Чому перевірка її не зловила?
Так. У Z2 модель назвала реальний маршрут, але вказала 10 грн і 1 годину, тоді як у transport.csv вказано 854 грн і 3 години. Відповідь звучить правдоподібно, але неправильна. Перевірка виявляє, що маршрут у первинному виклику не знайдено; вона не перевіряє фактичну відповідь моделі на відповідність даним інструмента.

6. Які поламки перевірки не лікують у принципі?
Перевірки аргументів не гарантують, що модель правильно зрозуміла намір користувача, обрала потрібний інструмент або використала його результат у фінальній відповіді. Вони також не запобігають непідтвердженим твердженням, якщо модель відповіла без виклику інструмента. Для цього потрібні точніші інструкції, контроль фінальної відповіді та перевірка її відповідності результатам інструментів.

7. Скільки додаткових викликів моделі пішло на виправлення? Чи виправдана ціна?
За логами в обох прогонах за задачами є по 8 викликів моделі: Z1 — 2, Z2 — 2, Z3 — 2, P1 — 1, P2 — 1. Отже, за цим порівнянням приріст становить 0 додаткових викликів. У Z2 після перевірки наступний виклик усе одно дав неправильні дані, тому в цьому випадку додатковий крок не забезпечив правильного результату. Ціну надійності варто оцінювати разом із якістю відповіді, а не лише за кількістю викликів.

8. Що видно в найдовшій трасі та чому довгий текстовий лог важче читати?
У прогоні checks найдовшою за часовими мітками виглядає Z2: від початку задачі до фінальної відповіді минуло приблизно 17 секунд. У трасі Langfuse зручно побачити дерево кроків, окремі виклики моделі та інструмента, їхні входи й виходи, токени й тривалість. У текстовому лозі зручніше послідовно прочитати повідомлення про рівень помилки та відповідь агента. На довгих задачах лог ускладнюється, бо записи кроків, аргументів, результатів і відповідей накопичуються в одному текстовому потоці.

У тесті модель qwen2.5:3b через Ollama повернула JSON, який відповідає схемі search_routes: поле query є рядком, і model_validate_json() успішно створив Pydantic-об’єкт. Це підтверджує, що цей запит спрацював із response_format.
Але перевірку в коді краще не прибирати. response_format задає моделі потрібну структуру, а model_validate_json() додатково перевіряє фактичну відповідь. Крім того, відповідність схемі не означає змістову правильність: у прикладі все речення потрапило в query, хоча очікувався короткий пошуковий запит. Для змісту потрібні окремі правила.
Отже, перевірку формату можна було б вважати дублюванням лише за надійної гарантії суворого дотримання схеми сервером, але перевірки змісту все одно слід залишити. Для конфігурації безпечніше зберегти model_validate_json().

### Висновок
Найбільший ефект дала перевірка змісту аргументів: у задачі Z2 вона виявила, що передана назва маршруту відсутня в довіднику, і повернула моделі перелік доступних маршрутів. Проте це не гарантувало правильної відповіді: модель повторно не перевірила дані й вигадала ціну та тривалість поїздки. Отже, перевірки допомагають виявляти помилки у викликах інструментів, але самі по собі не забезпечують правильного фінального тексту.
