## 1. Вихідні дані та підготовка проєкту

Для виконання лабораторної роботи використано агента, розробленого в лабораторній роботі №2 за варіантом 7 «Подорожі».

Агент відповідає на запитання про подорожі, підбирає маршрути вихідного дня та розраховує бюджет поїздки. Для цього використовуються три основні інструменти та один заборонений для перевірки обмежень:

- `search_routes` – пошук маршрутів вихідного дня за категоріями;

- `transport_info` – отримання інформації про транспорт із довідника;

- `calc_budget` – розрахунок загального бюджету поїздки з урахуванням кількості людей та додаткових витрат;

- `buy_ticket ` — заборонена дія (купівля квитків), яка блокується диспетчером для перевірки безпеки та прав доступу.

У роботі використано локальну модель qwen2.5:3b через Ollama. У фінальному прогоні використано такі значення параметрів моделі:

- `MAX_STEPS = 6`

- `TEMPERATURE = 0.2`

Для перевірки роботи агента використано ті самі п'ять завдань: Z1, Z2, Z3, P1 та P2. Під час доопрацювання було змінено описи функцій у schemas.py, правила валідації та повідомлення у checks.py ; тому порівняння описує фактичні версії, а не ізольований вплив однієї зміни.

## Класи аргументів (`arguments.py`)

```python
"""Класи аргументів інструментів."""
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field


class SearchRoutesArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    query: str = Field(description="Пошуковий запит для маршруту українською")


class TransportInfoArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    route: str = Field(description="Назва маршруту")


class CalcBudgetArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    price_per_person: float = Field(gt=0, description="Ціна квитка на одну особу в один бік")
    people: float = Field(gt=0, description="Кількість людей")
    extra: float = Field(ge=0, description="Додаткові витрати")


ARGS = {
    "search_routes": SearchRoutesArgs,
    "transport_info": TransportInfoArgs,
    "calc_budget": CalcBudgetArgs,
}
```

## Відповіді на питання

1. За результатами прогонів (табл. 4–5), синтаксичних поламок (syntax) та порушень JSON-схеми (schema) не виникало в жодній із задач як до, так і після впровадження перевірок. Після додавання валідації спрацював лише рівень meaning на задачі Z2 (1 раз), коли модель звернулася до неіснуючого маршруту в довіднику, після чого отримала підказку й успішно сформувала коректну відповідь.

2. Найчастіше модель помилялася на рівні семантики (meaning) та валідації параметрів інструментів. Щоб це зменшити, найефективніше перенести жорсткі обмеження безпосередньо у Pydantic-схеми (ConfigDict(extra="forbid")) або детальніше розписати інструкції в описах функцій.

3. Захисний ліміт (MAX_RETRIES та MAX_STEPS) не спрацював у жодному з тестових прогонів (табл. 4): усі задачі завершувалися за 1–2 виклики моделі без зациклень, а після спрацювання перевірки meaning на задачі Z2 модель виправилася одразу на наступному кроці.

4. Так, іноді модель підставляла схожий за назвою міської локації тариф чи параметр, який технічно відповідав типам даних у схемі. Жодна перевірка її не зловила, оскільки валідатори перевіряють синтаксис та допустимість меж, але не можуть знати реального наміру користувача.

5. Перевірки не лікують концептуальні помилки планування та хибне розуміння предметної області. Програмний код валідатора перевіряє форму та відповідність довідникам, але не здатний замінити генерацію правильного стратегічного ланцюжка розв'язання.

6. Згідно з табл. 6, кількість викликів моделі на всіх задачах не збільшилася (залишилася на рівні 2 для Z1–Z3, P1 та 1 для P2), а витрати токенів змінилися в межах похибки (наприклад, для Z3: з 1582 до 1585 токенів). Навіть у випадку Z2, де спрацювала перевірка meaning, валідатор повернув повідомлення про відсутність маршруту прямо у відповіді інструменту на кроці 1, тому модель сформувала правильну відповідь на кроці 2 без додаткових ітерацій і зайвих витрат ресурсів.

7. У Langfuse найзручніше відстежувати дерево викликів, час виконання та загальну кількість використаних токенів по кроках. Водночас детальний текстовий лог краще демонструє весь сирий потік діалогу та проміжні аргументи, але на довгих задачах він перетворюється на величезний нечитабельний масив через сотні рядків повторюваних інструментальних логів.

## Висновок

Найбільший ефект дали перевірки змісту (meaning та permission) на тестах (test_checks.py) і в основному прогоні (lab3_checks.log), де на задачі Z2 перевірка meaning миттєво перехопила неіснуючий маршрут 'Кам'янць-Подільський' і допомогла моделі коректно відповісти за ті самі 2 виклики (1.08 с, 1628 токенів). Надалі варто додати нормалізацію пошукових запитів (через промахи на кшталт "историчні місця" у Z1), посилити системний промпт для перехоплення відмови від виклику інструментів у P2 (1 виклик, 738 токенів, 0 call_tool) та розширити тестовий набір задач.
