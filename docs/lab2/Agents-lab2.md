# Лабораторна робота № 2. Перший агент

## Мета

Написати програму, яка сама вирішує, які інструменти викликати, щоб відповісти на питання користувача.

## Що треба зробити

У вас є три готові інструменти: пошук, довідник і калькулятор.

Ви маєте написати програму, яка працює так:

1. передає моделі питання користувача і описи доступних інструментів;
2. модель відповідає, який інструмент викликати і з якими аргументами;
3. програма викликає цей інструмент і повертає моделі результат;
4. усе повторюється, поки модель не дасть готову відповідь.

Потім запустити цю програму на п'яти питаннях і записати, де вона помилилася.

## Хід роботи

Завдання індивідуальне: предметна область, перелік інструментів,
системне повідомлення та набір контрольних питань наведено
у файлі відповідного варіанта.

### Підготовка

Створіть каталог проєкту, віртуальне середовище Python
та встановіть бібліотеку `openai`.

Далі потрібно підготувати дані, з якими працюватиме агент.
Джерел два: корпус і довідник. Вони різні за призначенням,
і кожен обслуговує свій інструмент.

**Корпус** – набір текстових файлів з описовою інформацією.
У ньому шукають за змістом: користувач формулює запит своїми словами,
а інструмент пошуку знаходить відповідні записи.

**Довідник** – одна таблиця з точними значеннями. Тут нічого
не шукають за змістом: інструмент знаходить рядок за ключем
і повертає потрібні поля.

Дані вигадані, відповідність дійсності не перевіряється.
Писати їх вручну не потрібно – згенеруйте будь-яким чат-ботом.

### Крок 2. Інструменти

Мовна модель не має доступу ні до файлів, ні до бази даних,
ні до обчислень. Вона працює лише з текстом. Усе, що виходить
за межі тексту, робить ваша програма – і саме для цього потрібні
інструменти.

Інструмент – це звичайна функція Python. Вона читає дані з каталогу
`data/`, обробляє їх і повертає результат **рядком**: модель уміє
приймати тільки текст.

Далі в роботі ця функція буде викликатися не вами, а за вказівкою
моделі: модель повідомить, який інструмент їй потрібен і з якими
аргументами, а програма його викличе.

Створіть у каталозі проєкту файл `tools.py`. Вихідний код трьох
інструментів вашого варіанта наведено в текстовому файлі варіанта,
у розділах «Інструмент 1», «Інструмент 2» та «Інструмент 3».
Скопіюйте їх у `tools.py` без змін.

Зверніть увагу на два моменти в коді:

- шляхи до даних записані відносно каталогу проєкту (`data/corpus/`,
  `data/books.csv`), тому запускати програми треба саме з нього;
- якщо інструмент нічого не знайшов, він повертає не порожній рядок,
  а повідомлення про це – моделі потрібен текст, який вона зможе
  прочитати.

Після копіювання перевірте роботу кожної функції окремо, без моделі.
Для варіанта 1:

```python

print(tools.search_books("фантастика"))
print(tools.book_info("Основи алгоритмів"))
print(tools.calculate("mul", 5, 10))
```

Якщо `search_books` нічого не знаходить, а `book_info` повідомляє,
що книжки немає в довіднику, – найімовірніше, назви в корпусі
та довіднику не збігаються.

#### Реєстр інструментів

Модель не може викликати функцію – вона лише повідомляє її назву
рядком, наприклад `"book_info"`. Щоб за цим рядком знайти саму функцію,
потрібен словник: ключ – назва, значення – функція.

Такий словник називають реєстром інструментів. Додайте його в кінець
файлу `tools.py`:

```python
TOOLS = {
    "search_books": search_books,
    "book_info": book_info,
    "calculate": calculate,
}
```

Праворуч ім'я функції пишеться **без дужок**. З дужками ви записали б
у словник результат виклику, а потрібна сама функція.

Далі в програмі це працюватиме так:

```python
name = "book_info"                       # прийшло від моделі
func = TOOLS[name]                       # дістали функцію зі словника
result = func("Основи алгоритмів")       # викликали
```

Загальна структура файлу `tools.py`:

```python
import csv
import os


def search_books(query: str) -> str:
    ...


def book_info(title: str) -> str:
    ...


def calculate(operation: str, a: float, b: float) -> str:
    ...


TOOLS = {
    "search_books": search_books,
    "book_info": book_info,
    "calculate": calculate,
}
```

Назви інструментів у реєстрі мають дослівно збігатися з назвами
з розділу «Опис для моделі» у файлі вашого варіанта.

### Крок 3. Описи інструментів

Модель не бачить вашого коду. Вона не знає ні назв функцій,
ні того, що вони роблять. Щоб вона могла скористатися інструментом,
опис треба передати їй явно – у параметрі `tools` під час виклику:

```python
response = client.chat.completions.create(
    model=MODEL,
    messages=messages,
    tools=SCHEMAS,        # ось сюди
)
```

Отримавши цей список, модель читає описи й вирішує, який інструмент
підходить до поточного запиту. Тобто **вибір інструмента залежить
від того, як ви його описали**, а не від того, як написана функція.

#### З чого складається опис

Опис одного інструмента – це вкладений словник. Розберемо його
по шарах, від зовнішнього до внутрішнього.

**Шар 1.** Зовнішня обгортка. Однакова завжди:

```python
{
    "type": "function",
    "function": { ... }
}
```

**Шар 2.** Усередині `"function"` – три ключі:

```python
{
    "name": "назва функції",
    "description": "що робить і коли використовувати",
    "parameters": { ... }
}
```

`name` має дослівно збігатися з ключем у словнику `TOOLS`.

**Шар 3.** Усередині `"parameters"` – перелік аргументів:

```python
{
    "type": "object",              # завжди саме так
    "properties": { ... },         # опис кожного аргумента
    "required": ["список обов'язкових"]
}
```

**Шар 4.** Усередині `"properties"` – по одному запису на аргумент:

```python
"назва_аргумента": {
    "type": "string",              # string, number, integer або boolean
    "description": "що сюди передавати",
}
```

Якщо аргумент приймає лише кілька конкретних значень, додайте `enum` –
тоді модель обиратиме зі списку, а не вигадуватиме своє:

```python
"currency": {
    "type": "string",
    "enum": ["USD", "EUR", "PLN"],
    "description": "Валюта, з якої переводимо",
}
```

#### Що писати в текстах

Два поля з описом – `description` функції та `description` кожного
аргумента – це і є те, що читає модель. Решта полів технічні.

У `description` функції вкажіть: що вона робить, що повертає
і **коли її використовувати**. Останнє пропускають найчастіше,
а саме воно допомагає моделі обрати правильний інструмент.

У `description` аргумента вкажіть, у якому вигляді передавати значення.
Без цього модель може передати в пошук усе питання користувача цілком.

### Крок 4. Диспетчер

Модель не викликає функцій. Вона повертає два рядки: назву інструмента
і його аргументи. Наприклад:

```
name      = "book_info"
arguments = '{"title": "Основи алгоритмів"}'
```

Щоб перетворити це на реальний виклик, потрібен посередник –
**диспетчер**. Він робить чотири речі:

1. знаходить функцію в реєстрі `TOOLS` за назвою;
2. розбирає аргументи: вони приходять рядком, а функції потрібен словник;
3. викликає функцію;
4. повертає результат рядком, бо модель приймає лише текст.

Диспетчер – єдине місце в програмі, де можна щось перевірити
перед виконанням. Модель може попросити що завгодно: назвати
неіснуючий інструмент, передати зіпсований JSON або аргумент
не того типу. Виконається тільки те, що диспетчер пропустив.

#### Чому помилки не можна просто дати впасти

Якщо диспетчер кине виключення, програма зупиниться. Ви проганяєте
агента на п'яти питаннях, і на другому прогін обірветься – решта трьох
навіть не запуститься.

Тому диспетчер **завжди повертає рядок і ніколи не кидає виключення**.
Текст помилки потрапляє в контекст, і модель може прочитати його
на наступному кроці й виправитися.

#### Код

Створіть файл `dispatcher.py`:

```python
"""Виклик інструмента за назвою, отриманою від моделі."""
import json
from tools import TOOLS


def call_tool(name: str, args_raw: str) -> str:
    # модель могла назвати інструмент, якого не існує
    if name not in TOOLS:
        return (f"Помилка: інструмента '{name}' не існує. "
                f"Доступні: {', '.join(TOOLS)}")
    try:
        args = json.loads(args_raw)        # рядок -> словник
        return str(TOOLS[name](**args))    # ** розпаковує словник в аргументи
    except json.JSONDecodeError:
        return "Помилка: аргументи не є коректним JSON."
    except TypeError as e:
        return f"Помилка в аргументах: {e}"
    except Exception as e:
        return f"Помилка виконання: {e}"
```

Конструкція `**args` перетворює словник `{"title": "Основи алгоритмів"}`
на іменований аргумент `title="Основи алгоритмів"`.

Зверніть увагу на перше повідомлення про помилку: воно не просто
констатує проблему, а перелічує доступні інструменти. Модель прочитає
цей список і зможе виправитися.

Цей файл однаковий для всіх варіантів – нічого підставляти не треба.
Він працює з тим реєстром `TOOLS`, який ви склали на кроці 2.

```python
if __name__ == "__main__":
    print(call_tool("search_books", '{"query": "фантастика"}'))
    print(call_tool("delete_all", '{}'))

    print(call_tool("search_books", '{"text": "фантастика"}'))
```

повідомлення про помилку. Жоден не має завершитися виключенням.

Аргументи в цих прикладах записані так, як їх передає модель:
у вигляді рядка з JSON усередині. Другий випадок – неіснуючий
інструмент, третій – зіпсований JSON без лапок, четвертий –

### Крок 5. Цикл агента

На цей момент готові всі складові:

- `config.py` – налаштування;
- `tools.py` – функції інструментів і реєстр;
- `schemas.py` – описи для моделі;
- `dispatcher.py` – виклик інструмента за назвою.

Лишилося з'єднати їх у працюючу систему. Цим займається цикл.

#### Навіщо потрібен саме цикл

На питання «знайди щось легке з фантастики» вистачить одного виклику
інструмента. На питання «я затримав книжку на 5 днів, скільки штраф»
потрібні три: знайти книжку, дізнатися ставку, помножити.

Скільки саме викликів знадобиться, наперед не знає ніхто – це залежить
від питання й від того, що повернув попередній інструмент. Тому
послідовність не програмують, а повторюють однакову операцію,
поки модель не скаже, що готова відповісти.

#### Що робить один оберт циклу

1. Надіслати моделі всю історію повідомлень і описи інструментів.
2. Подивитися, що вона повернула:
   - якщо звичайний текст – це відповідь, виходимо з циклу;
   - якщо `tool_calls` – модель просить викликати інструмент.
3. Передати виклик диспетчеру.
4. Додати результат в історію з роллю `tool`.
5. Повернутися до пункту 1.

Ключова деталь: модель не має пам'яті. На кожному оберті їй передається
**вся історія заново**, тому результати попередніх викликів мають
накопичуватися у списку `messages`.

#### Ліміт кроків

Рішення зупинитися приймає модель. Вона може його не прийняти ніколи:
викликати той самий інструмент по колу або нескінченно уточнювати.

Тому замість `while True` використовуємо `for` зі скінченною кількістю
обертів. Якщо кроки скінчилися, а відповіді немає – зупиняємось
примусово. Значення ліміту вже лежить у `config.MAX_STEPS`.

#### Лог

У циклі відбувається багато чого, а назовні видно лише кінцеву
відповідь. Коли агент помилиться, без логу зрозуміти причину
буде неможливо.

Тому кожен крок записується: який інструмент викликано, з якими
аргументами, що повернулося. Функція друку передається в `run_agent`
параметром `log` – так її зручно замінити на запис у файл.

#### Код

Створіть файл `agent.py`:

```python
"""Цикл агента."""
from openai import OpenAI

import config
from schemas import SCHEMAS
from dispatcher import call_tool
from utils.lab_logger import custom_logger

client = OpenAI(base_url=config.BASE_URL, api_key=config.API_KEY)
logger = custom_logger('lab2')


def run_agent(task):
    """task – питання користувача
    Повертає текст відповіді або None, якщо вичерпано ліміт."""

    # історія розмови: системне повідомлення і питання
    messages = [
        {"role": "system", "content": config.SYSTEM},
        {"role": "user", "content": task},
    ]

    logger.info(f"\n{'=' * 60}")
    logger.info(f"ЗАДАЧА: {task}")

    for step in range(1, config.MAX_STEPS + 1):

        # 1. запит до моделі: передаємо ВСЮ історію заново
        response = client.chat.completions.create(
            model=config.MODEL,
            messages=messages,
            tools=SCHEMAS,
            temperature=config.TEMPERATURE,
        )
        msg = response.choices[0].message

        logger.info(f"\n--- крок {step} | prompt_tokens={response.usage.prompt_tokens}")

        # 2. немає tool_calls – модель дала відповідь, виходимо
        if not msg.tool_calls:
            logger.info(f"ВІДПОВІДЬ: {msg.content}")
            return msg.content

        # 3. пропозицію моделі кладемо в історію
        messages.append(msg)

        # 4. виконуємо кожен запитаний виклик
        for call in msg.tool_calls:
            logger.info(f"  виклик   : {call.function.name}({call.function.arguments})")

            result = call_tool(call.function.name, call.function.arguments)

            logger.info(f"  результат: {result}")

            # 5. результат повертаємо моделі з роллю tool
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": result,
            })

    # сюди потрапляємо, якщо цикл дійшов до кінця без відповіді
    logger.info("СТОП: вичерпано ліміт кроків")
    return None
```

Два місця, які варто розібрати окремо.

**`messages.append(msg)`** – у список додається сам об'єкт відповіді
моделі, а не словник. Без цього рядка модель на наступному оберті
не пам'ятатиме, що просила про виклик, і попросить знову.

**`tool_call_id`** – ідентифікатор конкретного виклику. Модель може
попросити кілька інструментів одразу, і за цим полем вона розуміє,
на який саме виклик прийшла відповідь.

#### Перевірка

Додайте в кінець файлу й запустіть `python agent.py`:


У виводі має бути видно принаймні один крок із рядками
«виклик» і «результат», а потім відповідь.

Далі спробуйте багатокрокове питання свого варіанта (задача Z3).
Агент має зробити кілька викликів поспіль, причому аргументи
кожного наступного залежатимуть від результату попереднього.

### Крок 6. Запуск на наборі питань

Агент уже працює, але запускати його по одному питанню незручно:
щоб оцінити поведінку, потрібен прогін на всьому наборі одразу,
а весь вивід має потрапити в один файл.

Цим займається окремий файл запуску. Він робить три речі: читає
питання зі списку, проганяє кожне через `run_agent` і записує
все, що відбувалося, у файл логу.

#### Файл із питаннями

Питання зберігаються окремо від коду, у форматі JSON. Так їх можна
змінювати, не чіпаючи програму.

Створіть файл `tasks.json` і перенесіть у нього п'ять питань свого
варіанта – три звичайні й дві пастки. Формат кожного запису:

```json
[
  {
    "id": "Z1",
    "question": "Знайди щось легке з фантастики",
    "expected": "назва книжки з корпусу, жанр фантастика, рівень легкий"
  },
  {
    "id": "Z2",
    "question": "Знайди книжку про сортування і скажи, чи є вона в наявності",
    "expected": "назва книжки та кількість примірників"
  }
]
```

Поле `question` передається агенту як питання користувача.
Поле `expected` агенту не передається – воно потрібне вам,
щоб потім звірити з ним фактичну відповідь.

#### Функція логування

В якості функції логування використовується `from utils.lab_logger import custom_logger`.
Вона дозволяє одночасно виводити повідомлення в термінал та лог-файл. 
Ім'я лог-файла задається під час ініціалізації логгера. Наприклад, `logger = custom_logger('lab2')`. 
Розширення файла `.log`.
Сам файл буде створений у тій же папці, де запускається програма.

#### Код

Створіть файл `agent_runner.py`:

```python
"""Прогін агента на всіх питаннях із tasks.json."""
import json
from agent import run_agent
from utils.lab_logger import custom_logger

logger = custom_logger('lab2')

with open("tasks.json", encoding="utf-8") as f:
    tasks = json.load(f)

    for task in tasks:
        logger.info(f"\n=== {task['id']} | очікується: {task['expected']}")
        run_agent(task["question"])

logger.info(f"\nОброблено задач: {len(tasks)}. Лог: lab2.log")
```

Перед кожною задачею в лог записується її номер і очікувана відповідь –
так при розборі одразу видно, що саме мало вийти.

#### Запуск

```
python agent_runner.py
```

Прогін на п'яти питаннях триває приблизно 5–10 хвилин: на кожне
питання припадає кілька звернень до моделі, а локальна модель
відповідає повільно.

Запускайте один раз. Далі працюйте з файлом `lab2.log` –
перезапускати агента, щоб щось передивитися, не потрібно.

## Результат роботи

### Таблиця поламок

Головний результат лабораторної. Відкрийте `lab2.log`, прочитайте
його від початку до кінця й порахуйте, скільки разів агент повівся
неправильно. Одна задача може дати кілька поламок одночасно.

| Поламка | Як упізнати в логу |
|---|---|
| Не викликав інструмент | на першому кроці немає рядка «виклик», одразу відповідь |
| Викликав не той інструмент | виклик є, але не той, що потрібен за умовою |
| Неправильні аргументи | у рядку «результат» слово «Помилка» |
| Зациклився | той самий виклик з тими самими аргументами двічі й більше |
| Не використав результат | інструмент повернув дані, у відповіді їх немає |
| Вигадав результат | у відповіді число або назва, яких немає в жодному «результат» |
| Вичерпав ліміт кроків | у логу рядок «СТОП» |

Остання колонка таблиці – загальна кількість по всіх п'яти задачах.

### Таблиця результатів

Для кожної з п'яти задач:

| Задача | Кроків | Викликів | Правильно (1/0) | Які поламки |
|---|---|---|---|---|
| Приклад завдання | 3 | 2 | 1 | |

Оцінку 1 або 0 ставите самостійно, звіряючи відповідь агента
з полем `expected`. Порівнювати рядки автоматично не можна:
агент напише «штраф становитиме 50 гривень» замість «50 грн».

Для задач-пасток оцінка 1 ставиться, якщо агент чесно повідомив,
що не може виконати запит.

### Розбір одного провалу

Оберіть найпоказовіший випадок і наведіть:

- номер задачі й текст питання;
- повний фрагмент логу без скорочень;
- яка відповідь мала бути;
- чому, на вашу думку, агент повівся саме так.

Пояснення «модель слабка» не приймається. Розгляньте конкретні
причини: опис інструмента не давав зрозуміти, коли його застосовувати;
модель не побачила, що потрібен другий крок; результат повернувся
у вигляді, який модель не змогла використати.

### Відповіді на питання

По одному-два речення:

1. Скільки задач із п'яти агент розв'язав правильно?
2. Яка поламка трапилася найчастіше?
3. Чи був випадок, коли агент вигадав результат, не викликавши інструмент?
4. Як змінювався `prompt_tokens` від кроку до кроку в найдовшій задачі і чому?
5. Чи пройшов агент задачі-пастки?
