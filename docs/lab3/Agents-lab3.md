### Крок 3. Аргументи інструментів класами Pydantic

У лабораторній роботі № 2 опис аргументів був записаний у `schemas.py` вручну і використовувався лише як підказка моделі. Але схема в запиті — підказка, а не гарантія: модель може її порушити. Щоб ті самі правила ще й перевірялися в коді, аргументи описують класами **Pydantic**. З класу генерується опис для моделі, і тим самим класом перевіряється її відповідь.

#### Класи аргументів

Створіть файл `arguments.py`. Нижче — приклад для двох вигаданих інструментів з лабораторної роботи № 2 (`get_weather` і `convert_currency`); класи для своїх трьох інструментів напишіть за тим самим зразком.

```python
"""Класи аргументів інструментів."""
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field


class WeatherArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    city: str = Field(description="Назва міста українською")


class CurrencyArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    amount: float = Field(gt=0, le=1000000, description="Сума, яку треба перевести")
    currency: Literal["USD", "EUR", "PLN"] = Field(description="Валюта, з якої переводимо")


ARGS = {
    "get_weather": WeatherArgs,
    "convert_currency": CurrencyArgs,
}
```

Кожна частина класу забороняє одну з помилок схеми:

- **тип поля** (`str`, `float`, `int`) забороняє неправильний тип. Рядок `"5"` замість числа Pydantic перетворить сам, а `"п'ять"` - відхилить;
- **поле без значення за замовчуванням** обов'язкове — це заборона відсутнього поля;
- **`extra="forbid"`** забороняє вигадані поля. Без цього рядка вигадане поле буде мовчки відкинуто, і ви не дізнаєтеся, що модель неправильно зрозуміла інструмент;
- **`description`** нічого не забороняє: це пояснення поля для моделі. Перенесіть сюди описи аргументів зі свого `schemas.py`.

Назви полів мають дослівно збігатися з назвами параметрів функцій у `tools.py`.

#### Описи для моделі з класів

Перепишіть `schemas.py`: залиште тексти описів функцій, а розділ `parameters` беріть з класу методом `model_json_schema()`:

```python
"""Описи інструментів для моделі, згенеровані з класів аргументів."""
import config
from arguments import ARGS

DESCRIPTIONS = {
    "get_weather": "Повертає поточну температуру в місті. "
                   "Використовуй, коли користувач питає про погоду.",
    "convert_currency": "Переводить суму з однієї валюти в гривні за поточним курсом. "
                        "Використовуй ЗАВЖДИ для переведення валют, не рахуй самостійно.",
}

SCHEMAS = []
for name in config.ALLOWED:
    SCHEMAS.append({
        "type": "function",
        "function": {
            "name": name,
            "description": DESCRIPTIONS[name],
            "parameters": ARGS[name].model_json_schema(),
        },
    })
```

Модель тепер отримує ту саму схему, якою перевірятиметься її відповідь. Правила записано один раз, і розійтися їм нема як.

Перевірте результат:

```python
from schemas import SCHEMAS
import json

print(json.dumps(SCHEMAS[0], ensure_ascii=False, indent=2))
```

У виводі мають бути `"additionalProperties": false` і список `required`.

### Крок 4. Правила змісту

Pydantic перевіряє форму аргументів. Але чи є значення у ваших даних і чи дозволена дія, знає лише ваш код. Частину таких правил можна записати прямо в класи, решта — в окрему функцію.

#### Заборонена дія

Додайте в `tools.py` четвертий інструмент — заборонену дію свого варіанта (табл. 7). Це заглушка, яка нічого не робить:

```python
def cancel_booking(booking_id: str) -> str:
    return "Бронювання скасовано"      # заглушка: агентові ця дія заборонена
```

Додайте її в реєстр `TOOLS`, але **не** додавайте в `config.ALLOWED`. Модель цього інструмента не побачить: його немає в `SCHEMAS`. Але «не передали» — не те саме, що «заборонили»: модель може вгадати назву або побачити її в історії. Тому заборону перевіряє диспетчер (крок 5).

#### Правила в класах

Межі чисел і переліки допустимих значень запишіть прямо в класи аргументів:

- **межі числа** - `Field(gt=..., ge=..., lt=..., le=...)`: більше, більше або дорівнює, менше, менше або дорівнює. В описі для моделі вони стануть `minimum` і `maximum`;
- **перелік значень** - `Literal[...]`, якщо допустимих значень небагато (до 10). В описі для моделі це стане `enum`.

Межі визначте самі, виходячи зі своїх даних і задач: кількість не буває від'ємною, ціна не буває нульовою тощо.

#### Правила в коді

Те, що не вміщується в схему, пишіть у функції `check_meaning` у новому файлі `checks.py`. Вона отримує назву інструмента та вже перевірені Pydantic аргументи і повертає текст помилки для моделі або `None`, якщо все гаразд. Приклад для інструмента погоди з довідником міст `data/cities.csv`:

```python
"""Перевірки змісту аргументів."""
import csv

with open("data/cities.csv", encoding="utf-8") as f:
    CITIES = [row["city"] for row in csv.DictReader(f)]


def check_meaning(name, args):
    if name == "get_weather":
        if args.city not in CITIES:
            return (f"Помилка: міста '{args.city}' немає в довіднику. "
                    f"Доступні: {', '.join(CITIES)}. "
                    "Виправ назву міста або повідом користувачу, що даних про це місто немає.")
    return None
```

Для свого варіанта перевірте щонайменше **ключ довідника**: значення, за яким інструмент шукає рядок, має бути в довіднику (табл. 7). Якщо допустимих значень більше десяти, не перелічуйте всі: напишіть, як отримати правильне значення (наприклад, «точну назву можна дізнатися пошуком»). Сюди ж ідуть правила, що залежать від кількох аргументів одразу.

Усі правила змісту зведіть у звіті в таблицю «Аргумент — правило — де записано (клас чи `check_meaning`) - звідки взято межу».

### Крок 5. Ланцюжок перевірок у диспетчері

Диспетчер з лабораторної роботи № 2 — єдине місце, де виклик можна перевірити перед виконанням. Тепер він перевіряє виклик по черзі та повертає два значення: **рівень**, на якому завершилась обробка, і **текст** для моделі. Які перевірки виконуються і до якого рівня помилок вони належать, показано в табл. 1.

Таблиця 1 — Перевірки диспетчера

| Порядок | Перевірка                         | Рівень у лозі | Рівень помилки                   |
|---------|-----------------------------------|---------------|----------------------------------|
| 1       | Чи існує інструмент               | `name`        | Схема                            |
| 2       | Чи дозволено його викликати       | `permission`  | Зміст                            |
| 3       | Чи розбираються аргументи як JSON | `syntax`      | Синтаксис                        |
| 3       | Чи відповідають аргументи класу   | `schema`      | Схема (і правила змісту з класу) |
| 4       | Чи мають значення сенс для даних  | `meaning`     | Зміст                            |
| 5       | Чи спрацював сам інструмент       | `tool`        | Помилка інструмента              |

Назва та дозвіл перевіряються раніше за аргументи: вони не залежать від аргументів, а перевіряти аргументи інструмента, якого немає або який заборонений, немає сенсу.

Перепишіть `dispatcher.py`. Цей файл однаковий для всіх варіантів:

```python
"""Перевірка і виконання виклику інструмента."""
from langfuse import observe
from pydantic import ValidationError

import config
from arguments import ARGS
from checks import check_meaning
from tools import TOOLS

# рівні, на яких помилилася модель (на відміну від "ok" і "tool")
MODEL_ERRORS = ["name", "permission", "syntax", "schema", "meaning"]


def format_validation_error(error):
    """Збирає з помилки Pydantic коротке повідомлення для моделі."""
    lines = ["Помилка: аргументи не пройшли перевірку."]
    for err in error.errors():
        if err["loc"]:
            field = err["loc"][0]
        else:
            field = "JSON"
        lines.append(f"Поле {field}: {err['msg']}")
    lines.append("Виправ аргументи і виклич інструмент ще раз.")
    return "\n".join(lines)


@observe(name="call_tool")
def call_tool(name, args_raw):
    # 1. чи існує інструмент
    if name not in TOOLS:
        return "name", (f"Помилка: інструмента '{name}' не існує. "
                        f"Доступні: {', '.join(config.ALLOWED)}. "
                        "Виклич один з доступних або повідом користувачу, що такої дії немає.")

    # 2. чи дозволено його викликати
    if name not in config.ALLOWED:
        return "permission", (f"Помилка: інструмент '{name}' недоступний. "
                              "Не повторюй виклик, повідом користувачу, що ця дія недоступна.")

    # 3. синтаксис і схема: Pydantic розбирає JSON і перевіряє поля
    try:
        args = ARGS[name].model_validate_json(args_raw)
    except ValidationError as error:
        level = "schema"
        for err in error.errors():
            if err["type"] == "json_invalid":
                level = "syntax"
        return level, format_validation_error(error)

    # 4. зміст: чи мають значення сенс для наших даних
    problem = check_meaning(name, args)
    if problem is not None:
        return "meaning", problem

    # 5. виконання
    try:
        return "ok", str(TOOLS[name](**args.model_dump()))
    except Exception as error:
        return "tool", (f"Помилка: інструмент '{name}' зараз не працює ({error}). "
                        "Не повторюй виклик, повідом користувачу.")


def check_response(choice):
    """Перевіряє відповідь моделі в цілому, до обробки викликів.
    Повертає None, якщо все гаразд, або (рівень, текст)."""
    # обрив: пояснювати нічого, просто повторити запит
    if choice.finish_reason == "length":
        return "length", None

    # зламаний виклик: модель хотіла викликати інструмент,
    # але зламала форму виклику, і сервер віддав його звичайним текстом
    msg = choice.message
    if not msg.tool_calls and msg.content:
        text = msg.content.strip()
        if "<tool_call>" in text or text.startswith("{"):
            return "syntax", ("Твоя відповідь схожа на виклик інструмента, але має неправильний формат. "
                              "Виклич інструмент ще раз через механізм інструментів "
                              "або дай відповідь користувачу звичайним текстом.")
    return None
```

Розберіть код. Зверніть увагу:

- **Повідомлення з трьох частин**: що не так, що допустимо, що робити далі. Для неіснуючого інструмента — зі списком доступних, для забороненої дії — з вказівкою не повторювати виклик.
- **Помилка інструмента** відрізняється від помилок моделі: модель не може її виправити, тому повідомлення каже «не повторюй», а не «виправ». Ваші інструменти читають локальні файли, тимчасових збоїв у них не буває, тому повторний виклик функції тут не реалізовано. Для інструментів, що звертаються до зовнішніх сервісів, його додають саме в цьому місці.
- **Обгортки навколо JSON** у tool calling не буває: аргументи сервер уже виділив з відповіді. Помилка синтаксису тут проявляється або як зламаний JSON в аргументах (рівень `syntax` у `call_tool`), або як зламаний виклик у тексті відповіді (`check_response`).
- **Декоратор `@observe(name="call_tool")`** робить кожен виклик диспетчера окремим вузлом у дереві траси Langfuse: з входом (назва та аргументи) і виходом (рівень і текст).

### Крок 6. Цикл агента з лімітом помилок

У лабораторній роботі № 2 модель могла помилятися скільки завгодно разів, доки не вичерпувався загальний ліміт кроків. Тепер з'являється окремий ліміт: якщо модель помилилася більше ніж `MAX_RETRIES` разів поспіль, агент чесно відмовляє. Помилки інструмента в ліміт не зараховуються — модель у них не винна.

Змініть `agent.py` так, як показано нижче. Нові рядки позначено коментарем `# НОВЕ`.

```python
"""Цикл агента з перевірками викликів."""
from langfuse import observe
from langfuse.openai import OpenAI

import config
from schemas import SCHEMAS
from dispatcher import call_tool, check_response, MODEL_ERRORS        # НОВЕ

client = OpenAI(base_url=config.BASE_URL, api_key=config.API_KEY)
logger = custom_logger('lab3')


@observe()
def run_agent(task, log):
    messages = [
        {"role": "system", "content": config.SYSTEM},
        {"role": "user", "content": task},
    ]
    retries = 0                                                       # НОВЕ: помилок моделі поспіль

    logger.info(f"\n{'=' * 60}")
    logger.info(f"ЗАДАЧА: {task}")

    for step in range(1, config.MAX_STEPS + 1):
        response = client.chat.completions.create(
            model=config.MODEL,
            messages=messages,
            tools=SCHEMAS,
            temperature=config.TEMPERATURE,
        )
        choice = response.choices[0]
        msg = choice.message

        logger.info(f"\n--- крок {step} | помилок поспіль={retries} "           # НОВЕ
                    f"| prompt_tokens={response.usage.prompt_tokens}")

        # НОВЕ: обрив або зламаний виклик у тексті відповіді
        problem = check_response(choice)
        if problem is not None:
            level, text = problem
            logger.info(f"  рівень   : {level}")
            logger.info(f"  текст    : {msg.content}")
            retries = retries + 1
            if retries > config.MAX_RETRIES:
                logger.info("СТОП: модель не змогла сформувати правильний виклик")
                return None
            if text is not None:
                messages.append({"role": "assistant", "content": msg.content})
                messages.append({"role": "user", "content": text})
            continue

        if not msg.tool_calls:
            log(f"ВІДПОВІДЬ: {msg.content}")
            return msg.content

        messages.append(msg)

        model_failed = False                                          # НОВЕ
        for call in msg.tool_calls:
            logger.info(f"  виклик   : {call.function.name}({call.function.arguments})")

            level, result = call_tool(call.function.name, call.function.arguments)   # НОВЕ

            logger.info(f"  рівень   : {level}")                              # НОВЕ
            logger.info(f"  результат: {result}")

            messages.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": result,
            })
            if level in MODEL_ERRORS:                                 # НОВЕ
                model_failed = True

        # НОВЕ: рахуємо помилки моделі поспіль
        if model_failed:
            retries = retries + 1
            if retries > config.MAX_RETRIES:
                logger.info("СТОП: модель не змогла сформувати правильний виклик")
                return None
        else:
            retries = 0

    logger.info("СТОП: вичерпано ліміт кроків")
    return None


if __name__ == "__main__":
    run_agent("Знайди щось легке з фантастики")
```

Що змінилося і чому:

- **`check_response`** перевіряє відповідь до обробки викликів. Обірвану відповідь не використовують і повторюють запит без пояснень: модель не помилилася. Зламаний виклик у тексті відповіді повертається моделі з поясненням з роллю `user` - без цієї перевірки агент показав би його користувачу як фінальну відповідь.
- **`call_tool` повертає два значення.** Рівень записується в лог: за ним на кроці 8 ви порахуєте, де модель помилялася.
- **Лічильник `retries`** рахує помилки моделі поспіль, обнуляється після успішного кроку і записується в лог біля кожного кроку. Окремого механізму повторної спроби немає: повторна спроба — це наступний оберт того самого циклу, на якому модель бачить у історії повідомлення про свою помилку.

Запустіть `python agent.py` і переконайтеся, що агент працює, а в лозі біля кожного виклику з'явився рядок «рівень».
